# AMQP 1.0 (OASIS Standard 2012, ISO/IEC 19464:2014)

## 0. Identity card

**Name / versions.** Advanced Message Queuing Protocol 1.0. One version: the protocol header carries `major=1, minor=0, revision=0` [3 §2.2, §2.8.19]. There is no 1.1; extension work ships as separate OASIS documents (sources 8-13).

**Governing body.** OASIS AMQP TC, with bindings and mappings in the separate AMQP-BINDMAP TC [1; 8]. Chairs at publication: Ram Jeyaraman (Microsoft), Angus Telfer (INETCO); editors Robert Godfrey (JPMorgan Chase), David Ingham (Microsoft), Rafael Schloming (Red Hat) [1].

**Specification documents.** Five parts plus an overview, all OASIS Standard 29 October 2012 [1]: Part 0 Overview [1], Part 1 Types [2], Part 2 Transport [3], Part 3 Messaging [4], Part 4 Transactions [5], Part 5 Security [6]. The same text is ISO/IEC 19464:2014, first edition 2014-05-01 [7]. It supersedes "AMQP v1.0 Final, 07 October 2011" from amqp.org [1].

**Year researched.** The 2012 OASIS text, extension drafts 2014-2021, broker documentation current at 2026-09-08.

**Reference implementation.** None named. Apache Qpid Proton (C plus Python/C++/Ruby bindings; 0.40.0, November 2024) is the de facto engine and is embedded in ActiveMQ Artemis and Qpid Dispatch [25; 30; 31].

**Wire type.** Binary, over a self-describing type system with format codes, described types and composite types; every performative and message section is a composite type in that system [2 §1.1-1.2; 3 §2.3.2].

**Transports the specification defines.** TCP only, IANA port `PORT` = 5672 and `SECURE-PORT` = 5671 for TLS-first ("amqps"). UDP and SCTP port assignments are reserved but "there are currently no UDP or SCTP mappings defined for AMQP" [3 §2.8.19]. TLS and SASL are layered by protocol-id in the 8-byte header: `%d2` TLS, `%d3` SASL, `%d0` bare AMQP [6 §5.2-5.3]. WebSocket is a separate Committee Specification 01 of 16 August 2016 [8].

**Relationship to AMQP 0-9-1.** AMQP 1.0 and AMQP 0-9-1 share a name, an IANA port and part of a committee lineage, and nothing else. They have different framing, type systems, lifecycle primitives and vocabularies: 0-9-1 has channels carrying `basic.publish` methods against a server-side model of exchanges, bindings and queues, while 1.0 has sessions carrying `transfer` performatives on named links between termini and defines no broker-side entity model at all. AMQP 1.0 is not a revision of 0-9-1 and there is no wire-level upgrade path; version negotiation exists precisely to make the mismatch fail fast [3 §2.2]. RabbitMQ shows the split concretely: it accepts both on port 5672 and dispatches on the protocol header into two separate implementations [14 "Version Negotiation"]. Everything below concerns 1.0; 0-9-1 has its own sheet.

## 1. Connection and session lifecycle

**Version negotiation.** Before any frame each peer sends 8 octets: ASCII `AMQP`, one protocol-id octet, then major/minor/revision [3 §2.2]. The TCP client MUST send immediately on connect; the TCP server MAY wait for the client's header first, which is how a multi-protocol server picks an implementation. An unsupported or unparseable version gets a header naming a supported version followed by a socket close, the server SHOULD choose the highest supported version less than or equal to the request. Protocol-id is not part of the version, so "highest supported" does not apply to it: a server requiring SASL answers a `%d0` request with `%d3` and closes, which is how a client learns a security layer is mandatory [3 §2.2].

**Security layers.** TLS: exchange `AMQP %d2 1.0.0`, negotiate TLS, exchange `AMQP %d0 1.0.0` inside it [6 §5.2]. The TLS client is the TCP client, MUST validate the server certificate and SHOULD send SNI; a pure TLS listener on 5671 with no prior header is the documented alternative [6 §5.2, §5.2.1]. SASL: exchange `AMQP %d3 1.0.0`, run the dialog in type-`0x01` frames, exchange `AMQP %d0 1.0.0` [6 §5.3]. Layers nest, so TLS-then-SASL-then-AMQP is the common deployment.

**Authentication.** The server sends `sasl-mechanisms` listing `sasl-server-mechanisms` in decreasing preference; an empty or null list is invalid and a server not requiring authentication SHOULD advertise exactly `ANONYMOUS`. The client answers `sasl-init` with `mechanism`, optional `initial-response` and optional `hostname`; zero or more `sasl-challenge`/`sasl-response` rounds follow; `sasl-outcome` carries `ok` (0), `auth` (1), `sys` (2), `sys-perm` (3) or `sys-temp` (4) [6 §5.3.2-5.3.3]. SASL frames are capped at `MIN-MAX-FRAME-SIZE` = 512 octets with no way to negotiate more, and an empty SASL frame is "an irrecoverable error" [6 §5.3.1].

**Connection open.** Each peer sends `open` on channel 0 as its first frame [3 §2.4.1]. Mandatory `container-id`; optional `hostname`, `max-frame-size` (default `4294967295`, i.e. no limit), `channel-max` (default `65535`), `idle-time-out`, `outgoing-locales`, `incoming-locales`, `offered-capabilities`, `desired-capabilities`, `properties` [3 §2.7.1]. Before negotiation the maximum frame size is 512 octets and the maximum channel number is 0; afterwards each peer MUST operate within mutually acceptable limits, and both MUST accept frames of at least 512 octets regardless [3 §2.4.1, §2.7.1]. A peer receiving offered capabilities it requires but that are absent MUST close the connection; a peer MUST NOT use a capability it did not list in `desired-capabilities` [3 §2.7.1].

**Pipelined open.** A peer MAY send frames after its own `open` without waiting, provided those frames are known a priori to conform to the partner's capabilities — in practice by staying inside what every implementation must support. The state machine has explicit `OPEN_PIPE`, `CLOSE_PIPE` and `OC_PIPE` states, and pipelined use is indistinguishable from non-pipelined use when the rule is honoured [3 §2.4.2, §2.4.6].

**Session begin.** Allocate an unused outgoing channel and send `begin` with `remote-channel` unset; the partner allocates its own outgoing channel and answers with `begin` carrying `remote-channel` set to the incoming channel it saw [3 §2.5.1]. Channels are unidirectional and independently numbered per direction, so the two halves of a session usually carry different numbers [3 §2.4]. `begin` carries mandatory `next-outgoing-id`, `incoming-window`, `outgoing-window` and optional `handle-max` (default `4294967295`) [3 §2.7.2]. Implementations are RECOMMENDED always to use the lowest free channel number [3 §2.5.1].

**Keep-alive and idle behaviour.** `open.idle-time-out` is milliseconds and states the maximum period the *sender of that open* wants between frames arriving from its partner. Each peer has an independent timeout, and the advertised value SHOULD be half the local threshold to avoid spurious expiry. Zero equals unset, and unset means no timeout — though the spec warns implementations MAY apply an internal default anyway [3 §2.4.5, §2.7.1]. A peer with nothing to send MAY emit an *empty frame* (header only, no body): SHOULD be channel 0, MUST be channel 0 before `open` has been received, may arrive on any valid channel, has no meaning beyond liveness, and may only be sent after `open` and before `close`. Alternatively it MAY send a `flow` for a valid session [3 §2.4.5]. On expiry a peer SHOULD close with `close(error=...)` and MAY then drop the socket; a peer that knows it has exceeded the *remote* threshold, e.g. because it is overloaded, SHOULD itself close with an explanation. The spec also says implementations SHOULD use TCP keep-alive "in order to be good citizens" [3 §2.4.5].

**Orderly close.** Session: `end`, optionally with `error`; the partner answers `end`. Sessions also end automatically when the connection closes or is interrupted [3 §2.5.2]. Connection: `close`, optionally with `error`, which MUST be the last thing ever written; the sender SHOULD keep reading until the partner's `close` arrives and SHOULD apply a timeout before dropping the transport. `close` MAY arrive on any channel up to `channel-max` but SHOULD be sent on channel 0 and MUST be if pipelined with `open`. Sockets SHOULD NOT be reused afterwards [3 §2.4.3]. Simultaneous close is legal at both levels; the only observable difference is which error code each side reports [3 §2.4.4, §2.5.3].

**Abortive close.** A session that cannot process input MUST send `end(error=...)` and then silently discard all incoming frames until the partner's `end` — the `DISCARDING` state [3 §2.5.4-2.5.5]; the connection has the analogous `DISCARDING` variant of `CLOSE_SENT` [3 §2.4.6]. An errored link endpoint MUST be detached with `detach(error=...)` and destroyed; any later input on that handle or its delivery-ids MUST end the session with `amqp:session:errant-link` [3 §2.6.5]. TLS implementations MAY use unidirectional shutdown, sending `close_notify` and closing the write half without waiting [6 §5.2].

**Reconnection rules the protocol defines.** Two. First, `amqp:connection:redirect` carries an `info` map with `hostname`, `network-host` and `port`; `amqp:link:redirect` adds `address` [3 §2.8.16, §2.8.18]. Over WebSocket the map gains optional `scheme` (`ws`/`wss`) and `path`, and a `wss` connection SHOULD NOT be redirected to `ws` [8 §3]. Second and far more important: link state is deliberately decoupled from connection state. Termini outlive link endpoints; a link with termini but no endpoints is *suspended*, and re-associating endpoints with surviving termini is *resuming* [3 §2.6] — see section 6. Reconnect timing, backoff and address discovery are unspecified.

**What an implementation run observed about `open` and about frames after a detach.** An acceptor's `open` carried `max-frame-size=262144`, `channel-max=255` and **no `idle-time-out` at all** [67]. The field is optional and its absence is not a default: a peer that arms a keep-alive clock from the partner's advertised value has nothing to arm, and the two thresholds are independent clocks rather than one negotiated number [3 §2.4.5]. A peer advertising nothing may still be reaped by an internal default, so absence is silence about the partner's own expectations and not permission to stay quiet forever.

The same run produced a `flow` naming a link handle **immediately after that link had been cleanly detached** [67]. This matters because §2.6.5's remedy — later input on an errored handle MUST end the session with `amqp:session:errant-link` — reads, applied to every unknown handle, as "end the session"; and the specification's other unknown-handle rule, `amqp:session:unattached-handle` [3 §2.8.17], reads the same way. [inference] The distinction the two rules actually draw is between a handle whose link was detached **with an error**, where later input is a fault, and a handle whose link was detached cleanly, where a frame already in flight is a race: the detach and the peer's next frame cross. An implementation that does not separate the two ends healthy sessions under normal detach traffic.

## 2. Primitives

**Container.** The outermost noun: a named entity (`container-id`, mandatory on `open`) holding nodes; brokers and client applications are both containers [3 §2.1.1, §2.7.1]. One per process by convention. Its identity must be stable across reconnects because link recovery is keyed on the `(source-container, target-container, link-name)` tuple [3 §2.6.1]. The Addressing draft strengthens this to "each container MUST use an AMQP network-unique container-id" and notes that the only protocol-level relevance of `container-id` is link recovery [10 §2.2, §2.4].

**Node.** A named entity inside a container responsible for safe storage and/or delivery; producers, consumers and queues are all nodes. A *distribution node* is one that stores messages for distribution [3 §2.1.1; 4 §3.3]. AMQP 1.0 defines no operation to create, configure, enumerate or delete a node — entirely out of scope of the core standard.

**Connection.** A full-duplex, reliably ordered frame sequence over one transport. Holds negotiated `max-frame-size`, `channel-max`, both idle timeouts, capability sets and the two channel maps [3 §2.1.2, §2.4]. 1..n sessions, up to `channel-max + 1`. Thirteen states from `START` to `END` [3 §2.4.6]. The ordering guarantee is exactly "if the nth frame arrives, all frames prior to n MUST also have arrived", with the explicit admission that connections are transient and can lose an unknown number of frames [3 §2.1.2].

**Channel.** Not user-visible: a unidirectional numbering slot in the connection's frame multiplex, carried in header bytes 6-7 [3 §2.3.2, §2.4]. Incoming and outgoing numbers are unrelated even for the same session.

**Session.** Correlates two unidirectional channels into a bidirectional sequential conversation. Holds the six flow-control variables, `handle-max` and the session-scoped delivery-id sequence [3 §2.5, §2.5.6]. Any number of links of any direction, but a link MUST NOT be attached to more than one session at a time [3 §2.5]. Seven states including `DISCARDING`, and no obligation to retain the endpoint once `UNMAPPED` [3 §2.5.5]. The shared delivery sequence exists for *aggregation*: one application receiving on many links can acknowledge sets of deliveries across all of them in a single `disposition` [3 §2.5].

**Link.** A unidirectional named route between two nodes, attached at each end to a terminus. Holds `name`, `source`, `target`, negotiated `snd-settle-mode` and `rcv-settle-mode`, `max-message-size`, the four flow-control variables and the local unsettled map [3 §2.6, §2.6.7, §2.7.3]. Names MUST uniquely identify the link among all links of the same direction between the two containers, so a link is active on one connection at a time; a second attach elsewhere "steals" it and the first MUST be closed with `amqp:link:stolen` — a rule that exists so that re-establishment works when only one party has noticed a failure. Names may be arbitrarily long because they only appear on `attach` [3 §2.6.1].

**Handle.** A per-endpoint numeric alias assigned by `attach` and used by `detach`, `flow`, `transfer`, `disposition`. The ends need not agree: the local choice is the *output handle*, the remote the *input handle*. Handles may be reused after close. Attaching on a handle already in use MUST be answered with an immediate `close` carrying `amqp:session:handle-in-use`; the lowest free handle is RECOMMENDED [3 §2.6.2, §2.7.3, §2.8.4].

**Terminus (source / target).** The stateful end of a link inside a node, whose primary responsibility is "to maintain a record of the status of each active delivery attempt until such a time as it is safe to forget" — the unsettled map [3 §2.6]. Sources track outgoing messages, targets incoming. Holds `address`, `durable`, `expiry-policy`, `timeout`, `dynamic`, `dynamic-node-properties`, `capabilities`, and for sources also `distribution-mode`, `filter`, `default-outcome`, `outcomes` [4 §3.5.3-3.5.4]. Termini outlive link endpoints, sessions and connections according to their expiry policy.

**Delivery.** One attempt to transfer one message, identified by a `delivery-tag` (up to 32 octets of binary chosen by the sending application, unique among all deliveries either end could consider unsettled on the link) and aliased on the wire by a session-scoped `delivery-id` [3 §2.6, §2.6.12, §2.8.7]. Created by the sending application; each end forgets it independently by settling. Settling is idempotent and one-way — unsettled to settled, never back [3 §2.6].

**Transaction controller / coordinator.** One container acts as *transaction controller*, the other as *transactional resource*. The resource exposes a `coordinator` target and the controller attaches a *control link* to it. No transactional work is allowed on the control link, and links to a coordinator cannot be resumed [5 §4.1-4.2, §4.5.1].

## 3. Message model

**Framing.** Three areas: an 8-byte fixed header (4-byte `SIZE`, 1-byte `DOFF` data offset in 4-byte words, 1-byte `TYPE`, two type-specific bytes), a variable extended header of `DOFF*4 - 8` bytes (ignored for AMQP frames), and a body of `SIZE - DOFF*4` bytes. `TYPE` `0x00` is an AMQP frame, `0x01` a SASL frame; `SIZE` < 8 or `DOFF` < 2 is malformed [3 §2.3-2.3.2]. An AMQP frame body is one performative encoded as a described type, optionally followed by an opaque payload. Nine performatives: `open` (0x10), `begin` (0x11), `attach` (0x12), `flow` (0x13), `transfer` (0x14), `disposition` (0x15), `detach` (0x16), `end` (0x17), `close` (0x18) [3 §2.1.3, §2.3.2, §2.7].

**Size limits.** Connection: `open.max-frame-size`, default unlimited (`4294967295`), floor 512. A peer MUST NOT send frames larger than its partner can handle, and receiving an oversized frame MUST close the connection with `amqp:connection:framing-error` [3 §2.7.1]. Link: `attach.max-message-size` (`ulong`); zero or unset means no limit, and exceeding it gives `amqp:link:message-size-exceeded` [3 §2.7.3, §2.8.18].

**Multipart and streaming.** A delivery may span `transfer` frames with `more=true` on all but the last. Deliveries on *different* links may interleave; deliveries on the *same* link MUST NOT [3 §2.6.14]. `aborted` on the last transfer tells the receiver to discard everything so far; an aborted message is implicitly settled and `aborted` takes precedence over `more` [3 §2.6.14, §2.7.5]. On continuation transfers `delivery-id`, `delivery-tag` and `message-format` MAY be omitted but MUST NOT differ if present [3 §2.7.5]. This is genuine streaming: a receiver can observe a readable but incomplete delivery, which Proton exposes as `Delivery.partial`, with handlers guarding on `partial == false` before decoding [30].

**Message structure.** A *bare message* is what the sender supplied; an *annotated message* is what the receiver sees. Sections in order: `header`, `delivery-annotations`, `message-annotations`, `properties`, `application-properties`, body, `footer`. The bare message is `properties` + `application-properties` + body and is immutable in the AMQP network — no intermediary may change, insert, omit or re-encode any of its sections, which is what preserves hashes, HMACs and signatures over the binary encoding [4 §3.2]. The body is exactly one of: one or more `data` sections (opaque binary), one or more `amqp-sequence` sections, or a single `amqp-value` section [4 §3.2.6-3.2.8].

**Header** (`0x70`): `durable` (default false), `priority` (ubyte, default 4, higher is higher), `ttl` (milliseconds), `first-acquirer` (default false), `delivery-count` (uint, default 0) [4 §3.2.1]. `durable=true` is a demand, not a hint: a target unable to honour it MUST NOT accept the message and MUST reject with `amqp:precondition-failed` or, if the source disallows `rejected`, detach with that error. `ttl` is recomputed downward by each intermediary as the difference between now and the previously computed expiry, so looping messages eventually die. `delivery-count` counts prior *unsuccessful* attempts, is zero on first delivery, and non-zero means "might be a duplicate". Priority has an exact remapping formula for brokers with fewer than 10 levels, designed so that two priorities distinct on an m-level server stay distinct on an n-level server with n > m.

**Properties** (`0x73`), the interpreted immutable metadata: `message-id`, `user-id` (binary), `to`, `subject`, `reply-to`, `correlation-id`, `content-type`, `content-encoding`, `absolute-expiry-time`, `creation-time`, `group-id`, `group-sequence`, `reply-to-group-id` [4 §3.2.4]. `message-id` and `correlation-id` are one of ulong, uuid, binary or string [4 §3.2.11-3.2.14]. The spec authorizes deduplication on the former: "A broker MAY discard a message as a duplicate if the value of the message-id matches that of a previously received message sent to the same node". `user-id` is "the identity of the user responsible for producing the message" and "MAY be authenticated by intermediaries" — the only per-message identity in the protocol. `to` "identifies the node that is the intended destination" and "on any given transfer this might not be the node at the receiving end of the link".

**Application-properties** (`0x74`): a map with string keys and values restricted to simple types, explicitly excluding map, list and array. Intermediaries may filter and route on it [4 §3.2.5].

**Annotations.** `delivery-annotations` (`0x71`) travel one hop, sender to receiver; `message-annotations` (`0x72`) are aimed at the infrastructure and intermediaries MUST propagate them unless explicitly augmented or modified, e.g. by the `modified` outcome. Both are maps keyed by symbol or ulong; all ulong keys and all symbol keys not starting `x-` are reserved; keys starting `x-opt-` MUST be ignored if not understood, and any other unrecognized key MUST cause a detach with `amqp:not-implemented` [4 §3.2.2-3.2.3, §3.2.10]. The symbol key `"rejected"` in delivery-annotations is reserved for `error` values [4 §3.2.2]. `footer` (`0x78`) holds values computable only once the whole bare message is seen: hashes, HMACs, signatures, encryption detail [4 §3.2.9].

**Message identity and sequence numbers.** Four independent identifiers: `properties.message-id` (application-level, globally unique by convention); `delivery-tag` (≤32 octets, per link, identifying a delivery *attempt*); `delivery-id` (session-scoped 32-bit RFC-1982 serial number, a wire shorthand for the tag); and the implicit per-`transfer`-frame `transfer-id` used by the session window [3 §2.5.6, §2.6, §2.6.12, §2.8.7-2.8.10]. Plus two things called `delivery-count`: the link's, "despite its name, not a count" but a sequence number, and the header's, an actual count of failed attempts [3 §2.6.7; 4 §3.2.1]. `group-id`/`group-sequence` express application grouping the protocol does not interpret [4 §3.2.4].

**Message format.** `transfer.message-format` is 32 bits: upper three octets identify the format, the low octet its version, and any version is forwards compatible with higher ones. Part 3 defines exactly one, `MESSAGE-FORMAT` = 0 [3 §2.8.11; 4 §3.2, §3.2.16].

**Opaque versus interpreted.** The transport layer "assumes as little as possible about messages": to Part 2 a message is bytes in a payload [3 §2.6.11]. Part 3 makes `header`, `properties`, `application-properties` and the annotations interpretable; the body stays opaque. The Filter Expressions draft codifies the boundary — it covers header, delivery-annotations, message-annotations, properties, application-properties and footer, and puts body sections "intentionally out of scope" because they "may be large, unstructured and intentionally opaque to intermediary containers" [9 §2.1].

**What an implementation run observed about splitting and about the body's section.** A message of 8192 octets sent to a peer whose `open` advertised `max-frame-size=1024` crossed as several `transfer` frames with `more=true` and arrived at that peer as one message of 8192 octets [67]. The number a sender splits on is therefore the **partner's** advertised size and not its own, which follows from "a peer MUST NOT send frames larger than its partner can handle" [3 §2.7.1] but is worth stating as a measurement, because the two values are independent and a sender that split on its own would either waste frames or be closed with `amqp:connection:framing-error`.

The same run established that the *choice of body section* is part of the contract rather than a presentation detail. A receiver whose deserialiser was asked for a binary value rejected a body carried as one or more `data` sections with a descriptor mismatch: `data` (`0x75`) and an `amqp-value` (`0x77`) holding a `binary` are different descriptors, and Part 3 permits either as a body [4 §3.2.6-3.2.8]. Nothing in the standard makes one of them the encoding of "some bytes", so a sender and a receiver that disagree about which one they mean fail at the section descriptor with a whole, valid, well-framed message in hand [67].

## 4. Patterns and topologies

The core standard defines no patterns. It defines links between termini and leaves address semantics undefined; what follows comes from the extension drafts and the broker guides.

**Peer-to-peer attach.** Either peer may initiate `attach` in either role. The initiator names the link, picks a handle, declares `role` (`sender` = false, `receiver` = true) and supplies both `source` and `target`; the partner locates or creates the matching terminus and answers with its own `attach` [3 §2.6.3, §2.8.1]. A partner that will not provide a terminus answers with that field null, which establishes a link to a nonexistent terminus, and MUST then immediately detach [3 §2.6.3]. Authority is split: "the link is always considered to be between the source as described by the sender, and the target as described by the receiver", and each peer MUST verify for itself that the remote terminus meets its requirements — "the remote peer SHOULD NOT attempt to preempt whether the terminus will meet the requirements of its partner" [3 §2.6.3]. An endpoint that cannot create exactly the requested terminus MAY adjust properties but MUST then report what it actually created [3 §2.6.3]. A "minimal" source or target with every field unset is legal for containers that only produce or only consume [4 §3.5.3-3.5.4].

**Addressing.** `address` is an archetype the core spec leaves undefined; `address-string` is its only concrete provider [4 §3.2.15]. The Addressing draft (CSD 01, 17 March 2021) adds an AMQP URI syntax of scheme, network endpoint, scope identifier, path and parameters, with rules that matter to intermediaries: link addresses in `attach` SHOULD NOT carry a network endpoint and any present MUST be ignored; `properties.to` MAY carry one but every recipient MUST ignore it as a dispatch criterion, since access through different on-ramps to the same AMQP address is equivalent; `properties.reply-to` MAY carry one and recipients SHOULD prefer replying over the connection the request arrived on, falling back to an outbound connection to that endpoint [10 §3.2.1-3.2.3]. Schemes and default ports: `amqp` 5672, `amqps` 5671, `ws` 80, `wss` 443, plus a transport-independent `scope` scheme [10 §3.1].

**Per-broker addressing.**
- *RabbitMQ 4.x address format v2.* Targets are exactly `/exchanges/:exchange/:routing-key`, `/exchanges/:exchange` (routing key `""`), `/queues/:queue`, or AMQP null. The first three pin one destination for the whole link and the default exchange `""` is disallowed in either exchange form. `/queues/:queue` requires an existing queue and internally routes through `amq.default`, so it needs write permission on `amq.default`. Null target is the anonymous terminus: every transfer must carry `properties.to`, whose string must match one of the three non-null forms, and an unroutable transfer is settled `released`. The only valid v2 source is `/queues/:queue`. All names are RFC 3986 percent-encoded, e.g. `/exchanges/amq.direct/my-routing_key%2F123`. The 3.x "v1" grammar (`/exchange/:exchange/:routing-key`, `/exchange/:exchange`, `/topic/:routing-key`, `/amq/queue/:queue`, `/queue/:queue`, bare `:queue`, and `/queue` routing per transfer from `properties.subject`) is deprecated in 4.0 behind the `amqp_address_v1` deprecated feature; v1 `/queue/:queue` and `/exchange/...` sources auto-declared queues and bindings, v2 expects the application to declare topology itself [14 "Addresses", "Address v2", "Address v1"].
- *ActiveMQ Artemis.* An address has a routing type and zero or more queues; `ANYCAST` routes a message to one queue on the address, `MULTICAST` to every queue [43]. A non-dynamic link uses the remote target or source address as the queue name and auto-creates it if address settings permit (`auto-create-queues` default `true`, auto-created queues durable, non-temporary, non-transient) [41; 43; 44]. A receiver attaching to a multicast-only address is treated as a subscription and gets a subscription queue; terminus durability `unsettled-state` or `configuration` makes it durable and names it `container-id:link-name`, `none` makes it volatile [41]. Fully qualified queue names use `address::queue`, and `::` is reserved for that [43].
- *Azure Service Bus.* The terminus address *is* the entity: `myqueue`, or `mytopic/subscriptions/sub`. Receivers set `source`, senders `target`; Service Bus does not interpret the local node name AMQP requires on the other side [57].
- *Qpid Broker-J 10.1.0.* An AMQP 1.0 producer may target an exchange for exchange routing *or* target a queue directly for point-to-point delivery — explicitly contrasted with 0-8/0-9/0-9-1/0-10, where ingress must go through an exchange. An unroutable exchange transfer tries a configured alternate binding, then is discarded unless the sender requested target capability `REJECT_UNROUTABLE` or the exchange's `unroutableMessageBehaviour` is `REJECT` [35].
- *ActiveMQ Classic 6.3.2.* `queue://name` and `topic://name`; a bare name defaults to queue [56].

**Anycast versus multicast.** The protocol expresses this as `source.distribution-mode`: `move` transitions a message to ACQUIRED before transfer and to ARCHIVED once settled successfully, so it is gone for other links; `copy` leaves node state unchanged so other links can still get it [4 §3.5.2, §3.5.7]. A source MUST NOT resend a message already transferred to an ACCEPTED state — trivial for `move`, requiring retained state for `copy` (in practice, for an ordered node, a record of the most recent message transferred) [4 §3.5.2]. Brokers layer their own words on top: Artemis `ANYCAST`/`MULTICAST` [43]; Dispatch address distributions `balanced` (one receiver, balanced by rate of settlement), `closest` (nearest only), `multicast` (a copy to all), `unavailable` (reject messages *and* attaches), with `router.defaultDistribution` and per-address `distribution` both defaulting to `balanced` [26 §11.1; 27].

**Request/reply.** `properties.reply-to` names the reply node, `correlation-id` ties response to request, `reply-to-group-id` routes replies to a group [4 §3.2.4]; all are in the immutable bare message, so intermediaries cannot rewrite them. The JMS mapping maps `JMSReplyTo` to `reply-to` and `JMSCorrelationID` to `correlation-id`, requiring application string correlation identifiers to use `message-id-string` [13 §§3.2.1, 5.1]. Routing back through intermediaries follows the Addressing rule above [10 §3.2.3].

**Dynamic reply nodes.** `source.dynamic=true` from a receiver, or `target.dynamic=true` from a sender, requests that the *partner* create a node; the requester MUST NOT set `address` and the creator MUST return the generated address, which SHOULD embed the link name and the remote `container-id` for traceability [4 §3.5.3-3.5.4]. `dynamic-node-properties` carries desired then actual properties including `lifetime-policy` — `delete-on-close`, `delete-on-no-links`, `delete-on-no-messages`, `delete-on-no-links-or-messages` — and `supported-dist-modes`; a dynamic node's lifetime is never shorter than that of the link that created it [4 §3.5.9-3.5.13]. Artemis implements a dynamic link as a temporary queue whose name it writes back into the address, removing it on link close for `link-detach` or `session-end` expiry policy [41; 54]. The JMS mapping uses a dynamic target plus `delete-on-close` for temporary destinations [13 §§5.1-5.3].

**Filters and selectors.** `source.filter` is a `filter-set`: a symbol-keyed map whose values are null or described types providing the `filter` archetype. A message passes iff it passes every named filter, a null value being a no-op; a filter MUST NOT change its answer for a message unless the state or annotations at the node change. The receiver sets its desired filter, the sender sets the filter actually in place including node defaults, and the receiver MUST check the result and detach if it does not meet its needs [4 §3.5.1, §3.5.8]. Filter types are an extension point advertised through source capabilities. Concrete filters:
- Apache's *proposed* filters: `apache.org:selector-filter:string`, code `0x0000468C:0x00000004`, JMS selector syntax with JMS headers translated to AMQP names (`JMSCorrelationID = 'abc'` becomes `amqp.correlation_id = 'abc'`) while application properties keep their own names, advertised as connection capability `APACHE.ORG:SELECTOR`; and `apache.org:no-local-filter:list`, code `0x0000468C:0x00000003`, capability `APACHE.ORG:NO_LOCAL`, admitting only messages originally sent to the source container on a different connection [33].
- OASIS Filter Expressions CSD 01: group filters `amqp:all-filter` (`0x...0100`), `amqp:any-filter` (`0x...0101`), `amqp:not-filter` (`0x...0102`); property filters `amqp:header-filter` (`0x...0170`), `amqp:delivery-annotations-filter` (`0x...0171`), `amqp:message-annotations-filter` (`0x...0172`), `amqp:properties-filter` (`0x...0173`), `amqp:application-properties-filter` (`0x...0174`), `amqp:footer-filter` (`0x...0178`); constants `amqp:true-filter` (`0x...0110`), `amqp:false-filter` (`0x...0111`); and `amqp:sql-filter` (`0x...0120`), an SQL-92-derived selector language. Property filters support `&p:`/`&s:` prefix/suffix modifiers and are case-sensitive throughout. Capabilities `AMQP_FILTEX_SQL_V1_0`, `AMQP_FILTEX_PROP_V1_0`, `AMQP_FILTEX_GROUP_V1_0` are negotiated per type-group on `open` or `attach`. A definitional error MUST make the source detach, typically with `amqp:invalid-field`; an evaluation error makes the message ineligible for delivery, and the implementation MAY move it elsewhere for diagnosis [9 §§2.1-2.3, 3, 4, 5, 6].
- RabbitMQ supports AMQP filter expressions only for stream sources: 4.1 added a subset of Working Draft 09 (properties and application-properties filters); 4.3 documents CSD 01 plus SQL, with property and SQL filters mutually exclusive. Separately it offers Bloom filtering via the `x-stream-filter-value` annotation and a `rabbitmq:stream-filter` receiver filter (string or ORed list), with `rabbitmq:stream-match-unfiltered=true` to include messages carrying no filter value; `x-stream-filter-size-bytes` defaults to 16 and ranges 16-255. An invalid filter at attach is simply omitted from RabbitMQ's answering attach (possibly with a log warning), leaving the client to detach and report [14; 19; 20; 24].
- Service Bus uses a `com.microsoft:session-filter` source filter key; a null session identifier makes it select the first available message and return the assigned session. Proton's example comments that a bare AMQP string is technically not a valid filter-set value unless described and that this may change [37].

**Shared and durable subscriptions.** No core mechanism. Qpid's design offers broker capability `SHARED-SUB`, derives `shared`/`global` from source capabilities (falling back to link capabilities when no source is present), and returns `topic`, `shared` and/or `global` in the answering source's capabilities, using `resource-locked` for an incompatible existing queue and `not-found` for a missing subscription queue [34]. The JMS mapping maps JMS `ClientID` to `open.container-id` [13 §2.1]. Artemis names a multicast receiver's subscription queue from `container-id:link-name`, with `amqp-use-core-subscription-naming` (default `false`) switching to CORE-aligned naming [41; 52].

**Qpid Dispatch router topology.** Dispatch is not a broker: "it never assumes ownership of a message", and it propagates settlement and disposition across the network so end-to-end guarantees hold without any persistent store; a broker is needed only when store-and-forward is genuinely required [29; 26 §2.2]. Interior routers run link-state routing similar to OSPF/IS-IS, compute best paths and recover through redundant paths rather than clustering; on an established inter-router connection traffic is bidirectional and listener-versus-connector only decides who opens the TCP connection, with exactly one connection per router pair recommended. `router.mode` defaults to `standalone`; `interior` participates in path computation, `edge` attaches without forcing recomputation. Inter-router links carry capability `qd.router` (control) or `qd.router-data` (message-routed user transfers), with `helloIntervalSeconds` 1, `helloMaxAgeSeconds` 3, `raIntervalSeconds` 30, `raIntervalFluxSeconds` 4, `remoteLsMaxAgeSeconds` 60 [26 §§4-5; 27].

*Message routing* looks at the delivered message's `to` address and resends it on zero or more outgoing links; pre-settled transfers stay pre-settled, and for unsettled ones the router keeps the ingress-to-egress association and propagates disposition and settlement in both directions. Address syntax is opaque to Dispatch [28]. *Link routing* matches an inbound sender's `target.address` or an outbound receiver's `source.address` at attach time, propagates the attach along a route and builds an end-to-end chain of paired link termini; thereafter transfers, dispositions and link state pass through the chain, so endpoints see a point-to-point link, credit is end-to-end, and server-side selectors and broker interpretation of `modified(undeliverable-here=true)` become available [28; 26 §§2.3, 11.2]. Message routing aggregates destinations by address and provides anycast/multicast distribution; link routing routes only the initial attach and performs no message-level aggregation, though multiple reachable link-route destinations can be balanced when the link is first routed [26 §11.2].

*Waypoints and autolinks* attach a router mesh to a broker queue by message routing, not link routing. An `autoLink` is router-managed with required `address` and `direction` (`in` into the router, `out` out of it), `phase` defaulting to 0 for `out` and 1 for `in`, and optional `containerId` XOR `connection`, `externalAddress`, `fallback`. With a waypoint address plus inbound and outbound autolinks, client links terminate on the router and the broker queue sees exactly one producer and one consumer regardless of client count [27; 26 §11.1.3]. `linkRoute` uses `prefix` XOR `pattern`, optional `addExternalPrefix`/`delExternalPrefix`, `containerId` XOR `connection`, required `direction`, and its only distribution is `linkBalanced`; individual client links remain separate broker producer/consumer links [27; 26 §11.2.2]. Address matching uses `prefix` or a wildcard `pattern` where `*` matches one `/`-delimited token and `#` zero or more, precedence exact > `*` > `#`; other `address` attributes are `distribution`, `waypoint`, `ingressPhase`, `egressPhase`, `priority`, `enableFallback` [27]. The guide recommends link routing when consumer semantics such as `modified(undeliverable-here=true)` matter, and warns that after a route-container connection loss a transfer may come back `RELEASED` or `MODIFIED` and clients should normally resend [26 §11.1.3].

**When there is nobody to talk to.** Core: a link with no source never produces messages and a link with no target never permits incoming ones [3 §2.7.3]; a refused terminus means immediate detach [3 §2.6.3]; an unresolvable address gives `amqp:link:redirect` or `amqp:not-found` [3 §2.8.15, §2.8.18]. Dispatch, storing nothing, grants a producer credit only while at least one consumer can receive, so without a consumer the sender waits; a delivery that reached no destination ends `released`, unless per-address `enableFallback=true` diverts it to a fallback destination attached with `autoLink{fallback: true}` or link capability `qd.fallback` [26 §11.1.1; 27]. RabbitMQ settles an unroutable anonymous-terminus transfer `released` [14].

## 5. Flow control and backpressure

AMQP 1.0 has two independent, simultaneously active credit schemes: per-link, counted in **messages**, and per-session, counted in **transfer frames**. Both are strictly receiver-granted. There is no per-connection credit.

### 5.1 Link credit

**Unit.** One unit of `link-credit` permits `delivery-count` to advance by one, i.e. one message [3 §2.6.7]. Because a message may span many frames, link credit says nothing about bytes.

**State** — four variables per link endpoint [3 §2.6.7]:
- `delivery-count` — initialized by the *sender* at an arbitrary point, communicated in `attach.initial-delivery-count` (MUST NOT be null for a sender, ignored for a receiver), incremented whenever a message is sent. Only the sender may independently modify it. A 32-bit RFC-1982 serial number, not a count; it wraps and compares by serial arithmetic [3 §2.6.7, §2.7.3].
- `link-credit` — "the current maximum legal amount that the delivery-count can be increased by". Only the *receiver* may independently choose it.
- `available` — how much credit the *sender* could use, i.e. its backlog. Only the sender may independently set it. The sender MAY transfer even when `available` is zero, in which case the receiver MUST floor its own calculation at zero.
- `drain` — a boolean set only by the receiver.

**Who grants, and the arithmetic.** The receiver sends `flow` carrying `handle`, `delivery-count` (its last known value of the sender's), `link-credit`, `drain`, `echo`. The sender then recomputes

```
link-credit_snd := delivery-count_rcv + link-credit_rcv - delivery-count_snd
```

If the receiver does not yet know a `delivery-count` — it has not seen the sender's `attach` — that field MUST NOT be set and the sender assumes the `initial-delivery-count` it sent [3 §2.6.7]. That formula is the whole design: what the receiver communicates is an absolute *delivery-limit* = `delivery-count + link-credit`, not an increment, so `flow` frames are idempotent and lost or reordered credit grants cannot inflate credit. RabbitMQ states the operational consequence plainly: link credit "is set, not accumulated" by each `flow` [16]. Whenever the sender increases `delivery-count` it MUST decrease `link-credit` by the same amount, preserving the limit [3 §2.6.7]. When a `flow` from the sender carries link state, `delivery-count` MUST be the sender's current value; from receiver to sender it MUST be the last known value of the sender's, and MUST NOT be set at all if the receiver has not yet seen the sender's `attach` [3 §2.7.4].

**At zero.** "If the link-credit is less than or equal to zero, i.e., the delivery-count is the same as or greater than the delivery-limit, a sender MUST NOT send more messages." The sender pauses: nothing is dropped, nothing disconnects [3 §2.6.7, Figure 2.40]. If the receiver *reduces* credit while transfers are in flight, it MAY either handle the excess normally or detach the link with `amqp:link:transfer-limit-exceeded` — its choice, not announced in advance [3 §2.6.7, §2.8.18].

**Initial state.** `link-credit` = 0, `available` = 0, `drain` = false. A freshly attached link therefore carries no permission to send anything until the receiver issues `flow` [3 §2.6.7] — RabbitMQ in broker terms: a consumer must send `flow` with link credit before the broker may transfer at all [16].

**Drain.** `drain=true` tells the sender: after sending everything available, advance `delivery-count` as far as possible, consuming *all* remaining `link-credit`, and report the new flow state. With nothing available the sender MUST advance `delivery-count` until `link-credit` is zero and send its updated `flow` [3 §2.6.7]. Drain converts "wait for a message" into "wait for a definite answer": the receiver learns unambiguously whether credit was consumed by a message or by drain, which is how synchronous-get-with-timeout is built — `flow(link-credit=1)`, wait, `flow(drain=true)`, wait for credit to reach zero [3 §2.6.8]. Proton exposes `Receiver.drain(n)` to grant credit and set drain mode, `drained()` to release or read back excess credit, and `draining()`, true only while drain mode is set and excess credit remains [30].

**Echo.** `flow.echo=true` asks the partner to send its state at the earliest convenient opportunity. With `handle` unset only session state need be echoed, though a link-carrying `flow` satisfies it too because any such frame also carries session state. Several echo requests before a reply MAY be answered once. The spec warns that answering an echo with an echo can loop forever and such a policy SHOULD be avoided [3 §2.7.4]. The canonical use is stopping a link: `flow(link-credit=0, echo=true)`; in-flight transfers may still arrive until the sender processes the new state, and the echoed `flow` marks the point after which no further transfer will come [3 §2.6.10] — the sequence RabbitMQ documents for pausing a consumer [16].

**Usage patterns the spec names** [3 §2.6.7-2.6.10]: synchronous get, `flow(link-credit=1)` then block; timed get, as above plus `flow(drain=true)`; asynchronous notification, keep a target credit level and top up with `flow(link-credit=delta)` when the sender's credit falls below a threshold, so that "the incoming message rate for the link is limited by the rate at which the receiver updates the delivery-limit"; stop, `flow(link-credit=0)`.

### 5.2 Session windows

**Unit.** One unit of window permits one `transfer` *frame*. Since frames are size-capped this is byte control in disguise: "Since frames have a maximum size for a given connection, this provides flow control based on the number of bytes transmitted and can be used to optimize performance" [3 §2.1.2, §2.5].

**State** — six variables per session endpoint [3 §2.5.6]: `next-incoming-id`, the expected transfer-id of the next incoming `transfer`; `incoming-window`, the maximum number of incoming transfer frames currently receivable, identifying a current maximum incoming transfer-id of `incoming-window + next-incoming-id - 1`; `next-outgoing-id`, the transfer-id for the next outgoing frame, initializable arbitrarily and advanced by RFC-1982 serial arithmetic; `outgoing-window`, the maximum number of outgoing transfer frames currently sendable; `remote-incoming-window`, how many transfers may be sent without exceeding the partner's incoming window, decremented on every send and recomputed on `flow`; and `remote-outgoing-window`, how many may arrive without exceeding the partner's outgoing window, decremented on every receive and recomputed on `flow` — "When this window shrinks, it is an indication of outstanding transfers. Settling outstanding transfers can cause the window to grow."

**Updates** [3 §2.5.6]. Sending a transfer: increment `next-outgoing-id`, decrement `remote-incoming-window`, and MAY (by policy) decrement `outgoing-window`. Receiving one: set `next-incoming-id` to the incoming transfer-id plus one, decrement `remote-outgoing-window`, and MAY decrement `incoming-window`. Receiving a `flow`: set `next-incoming-id` from the frame's `next-outgoing-id`, set `remote-outgoing-window` from the frame's `outgoing-window`, and compute

```
remote-incoming-window = next-incoming-id_flow + incoming-window_flow - next-outgoing-id_endpoint
```

or, when the flow's `next-incoming-id` is unset (the peer has not seen `begin`),

```
remote-incoming-window = initial-outgoing-id_endpoint + incoming-window_flow - next-outgoing-id_endpoint
```

Violating the partner's incoming window is `amqp:session:window-violation` [3 §2.8.17]. Every `flow` carries mandatory `incoming-window`, `next-outgoing-id` and `outgoing-window`, so every link-level `flow` also refreshes session state; `begin` carries the same three mandatory fields as initial values, with no default [3 §2.7.2, §2.7.4].

### 5.3 How the two interact

Both must permit a transfer. Link credit bounds messages per link; the session window bounds frames across all links on the session. A receiver granting generous link credit but a tight incoming window forces the sender to dribble multi-frame messages; a receiver granting a large window but zero link credit gets nothing. The spec ties the two together nowhere and gives no guidance on relative sizing, which is where brokers differ most.

One under-specified corner: `delivery-id` is described as assigned by the *link* endpoint "from a session scoped sequence" [3 §2.6], while the session assigns each outgoing `transfer` *frame* an implicit `transfer-id` from its own session-scoped sequence [3 §2.5.6], and the relation between the two sequences is never stated. For single-frame deliveries they necessarily advance in lockstep; for multi-frame deliveries they cannot. [inference] Implementations uniformly derive both from one counter advancing per transfer frame, making a delivery's first `delivery-id` equal the transfer-id of its first frame; nothing in the standard requires this.

### 5.4 What brokers turn this into

**Prefetch is link credit.** Service Bus is explicit: a client receive maps to `flow(link-credit=1)`, and a non-zero `PrefetchCount` on `ServiceBusProcessor` or `ServiceBusReceiver` becomes link credit, giving push-style delivery; the legacy `MessageReceiver.PrefetchCount` default is `0`. The hazard is real: the lock clock starts when Service Bus removes the message from the entity, not when it puts it on the wire, so excessive credit can expire a lock before delivery. Service Bus selects the first available unlocked message, locks it and transfers it, retaining outstanding credit in arrival order when nothing is immediately available; in sender role it spends offered credit, in receiver role it initially offers ample credit and replenishes periodically by `flow` [57; 61]. ActiveMQ Classic maps an AMQP receiver to a JMS consumer, honours client credit and defaults to `1000` when the client sets none, with `transport.prefetch=10` overriding the client's preference [56].

**Publisher backpressure.** *RabbitMQ 4.x* grants an incoming publisher link 170 credits initially and another 170 when remaining credit drops below 85 and fewer than 170 messages are unconfirmed (`rabbit.max_link_credit` = 170). It keeps broker-internal confirms between session process and target queue even when it exposes no confirms to the client, so a queue that stops confirming promptly stops the credit grants — per-link backpressure. Session flow control is honoured, not ignored: a publisher may initially send 400 transfer frames, and after 200 are processed RabbitMQ sends `flow` with `incoming_window = 400` (`rabbit.max_incoming_window` = 400). To stop a large client link credit combined with a small client session window from buffering many transfers inside the session process, RabbitMQ grants its own queue process credit in batches of at most 256 (`rabbit.max_queue_credit` = 256), granting the next 256 only once those messages have left the session. Under a memory or disk alarm every session sends `incoming_window = 0`, blocking publisher transfers while consumer transfers and consumer-only connections keep working. The post labels 170/400/256 implementation details that may change [16]. The documented gain is per-link isolation: a slow target queue reduces grants on that publisher link only while other links on the same session continue, and a connection can publish and consume concurrently without a slow target link preventing receipt on source links — explicitly contrasted with 0-9-1 TCP reader backpressure, which affects the whole connection [16, benefits 3 and 4].

*Artemis* counts producer credit in messages, not bytes; source defaults are `amqpCredits = 1000` and `amqpLowCredits = 300`, topping a producer link up when remaining credit falls below the low-water mark, and the acceptor example configures exactly `amqpCredits=1000;amqpLowCredits=300` [41; 54]. The Flow Control guide's `BLOCK` narrative instead describes issuing 100 credits at a time and refreshing at 30 — a behaviour description that does not match the current default constants, and the two should not be collapsed into one number [42 versus 41; 54]. With `address-full-policy=BLOCK` Artemis stops issuing producer credit when the address is full, which is the backpressure; because credit counts whole messages, already-granted credit can overshoot a byte bound, hence `max-size-bytes-reject-threshold` (default `-1`, no limit) as an AMQP-only hard stop after which Artemis rejects messages. Other `address-full-policy` values are `PAGE` (default), `DROP` (silently discard) and `FAIL` (drop and throw client-side) [42; 44]. On the consumer side the broker sender computes available credit as `sender.getCredit()` minus pending deliveries and sends only while positive, returning 1 per delivery "because on AMQP we only send messages based in credits, not bytes" [54].

*Qpid Dispatch*, storing nothing, grants a producing sender credit only while at least one consumer can receive [26 §11.1.1]. `listener.linkCapacity` and `connector.linkCapacity` bound concurrent in-flight deliveries per internal link, but the 1.19.0 reference declares no default [27]. In a link route the actual receiver's credit propagates to the sender across the chain, so the router makes no independent credit decision [26 §11.2.1; 28]. [inference] Consumer-presence gating plus end-to-end link-route propagation is the whole documented multi-hop mechanism; no per-hop credit-window algorithm is specified. *Service Bus* "imposes no particular session-level throttling window and resets the session window as link flow control proceeds", leaning on link credit alone [57].

## 6. Delivery guarantees and acknowledgement

### 6.1 The mechanism

Every guarantee is built from one primitive pair: **delivery state** and **settlement**. Settlement means an endpoint has forgotten a delivery-tag; it is idempotent and irreversible [3 §2.6]. State is exchanged while a delivery is unsettled.

The full unsettled dance [3 §2.6.12, Figures 2.47-2.54]: (1) the sending application supplies message data and a `delivery-tag`; the sender creates an unsettled-map entry and sends `transfer(delivery-tag=DT, settled=false, state=S_0)`. (2) The receiver creates its own entry and hands the data to its application. (3) The receiving application MAY report non-terminal states via `disposition(role=receiver, settled=false, state=S_2)` — useful for large messages and transactions. (4) When done it reports a *terminal* state, the outcome it wants applied at the sender. (5) The sender updates its view and tells its application. (6) The sending application acts and settles: `disposition(role=sender, settled=true, state=T_1)`. The spec is blunt about what this means — "the sender announcing that it is forever forgetting everything about the delivery-tag in question, and as such it is only possible to make such an announcement once, since after the sender forgets, it has no way of remembering to make the announcement again"; if that frame is lost the receiver discovers the settlement on link recovery, by observing the tag's absence from the sender's unsettled map. (7) The receiver notes the remote settlement, notifies its application (which can now drop the tag from a dedup set) and settles locally without telling anyone, since the sender has already forgotten.

A sender MAY reach a terminal state spontaneously — TTL expiry, for instance. It SHOULD then send a `disposition` but SHOULD NOT settle until the receiver confirms with a `disposition` in the opposite direction [3 §2.6.12]. Once a `transfer` or `disposition` from the sender says a delivery is terminal, no later frame from the sender can change it [3 §2.7.5].

`disposition` carries `role`, `first`, optional `last` (defaulting to `first`), `settled`, `state`, `batchable`. One `disposition` may cover deliveries from many links on the session provided all have the indicated role — the aggregation the shared delivery sequence exists for. It may also refer to deliveries on links no longer attached: "as long as the links have not been closed or detached with an error then the deliveries are still 'live' and the updated state MUST be applied" [3 §2.7.6]. A sender-to-receiver disposition may even refer to an incomplete multi-frame delivery, though the spec discourages that in favour of carrying the state on the next `transfer` [3 §2.7.6]. `batchable` on `transfer` or `disposition` hints that the peer need not urgently communicate updated state, permitting artificial batching to save bandwidth; it is not part of the transfer state and is not retained across resumption [3 §2.7.5-2.7.6].

### 6.2 The three settlement combinations

Settlement policy may be fixed for a link, allowing optimized endpoint choices, or decided per delivery [3 §2.6.12].

`snd-settle-mode` (default `mixed`) [3 §2.8.2]: `unsettled` (0), all deliveries sent initially unsettled, so `transfer.settled` MUST be false or unset on every frame unless aborted; `settled` (1), all sent settled, so `transfer.settled` MUST be true on at least one frame per delivery, i.e. the delivery MUST be settled at the sender by the time it is fully transferred; `mixed` (2), the sender may mix.

`rcv-settle-mode` (default `first`) [3 §2.8.3]: `first` (0), the receiver settles spontaneously on arrival without waiting for the sender; `second` (1), the receiver MUST NOT settle until it has sent its `disposition` to the sender *and* received a settled `disposition` back. `transfer.rcv-settle-mode` may override per delivery but only downward: if the negotiated link value is `first`, setting `second` on a transfer is illegal. If the sender is sending settled, the field is ignored. It is not part of the transfer state and is not retained across resumption [3 §2.7.5].

**At-most-once.** The sending application settles *before* sending: `transfer(settled=true, state=T_0)`. The sender has announced up front that it has forgotten everything and will make no further attempt; if the message arrives the receiver has no obligation to send state updates, which "would be meaningless and ignored" [3 §2.6.12, Figure 2.55]. This is `snd-settle-mode=settled`.

**At-least-once.** Unsettled send, but the receiving application settles immediately on processing rather than waiting for the sender. If that `disposition` is lost, on link recovery the sender does not see the tag in the receiver's unsettled map, assumes loss and resends — "resulting in duplicate processing of the message at the receiver" [3 §2.6.12, Figure 2.56]. This is `snd-settle-mode=unsettled` with `rcv-settle-mode=first`.

**Exactly-once.** The scenario in 6.1 verbatim: the sender settles when the receiver reaches a terminal state, and the receiver settles when the sender settles. The spec states the general rule and both failure directions: "if the receiver settles prior to the sender, it is possible for duplicate messages to occur, except in the case where the sender settles before the initial transmission. Similarly, if the sender settles before the receiver reaches a terminal state, it is possible for messages to be lost" [3 §2.6.12]. This is `snd-settle-mode=unsettled` with `rcv-settle-mode=second`. The guarantee is *not* a property of the settlement modes alone: it depends on link resumption actually working, because the whole point is that a survivor of a connection failure can compare unsettled maps and decide correctly. Without resumption, `rcv-settle-mode=second` only removes the window in which the receiver forgets before the sender does.

**What an implementation run measured about `second`.** An acceptor configurable for the receiver settle modes it supports honoured `rcv-settle-mode=second` in its answering `attach` when configured to support both modes, and did not claim to honour it when configured for `first` only [67]. Two things follow. The mode is implementable, so the refusals recorded in §13 are properties of the brokers that publish them and not of AMQP 1.0 implementations as a class. And the answering `attach` is where a client learns which it got: the field is negotiated rather than requested, so an application that needs the three-way dance has to read the answer, and a peer restricted to `first` either answers with `first` or refuses the attach outright — both are legal and the difference is not something a client can predict [3 §2.7.3].

### 6.3 Link resumption and the unsettled map

`attach.unsettled` maps delivery-tag to delivery state for everything the issuing endpoint still considers unsettled; if either end already has a terminus, `attach` MUST include its unsettled state [3 §2.6.3]. Comparing both maps partitions the tags three ways [3 §2.6.13]: tags **only the source** considers unsettled MAY be resumed at the sending application's discretion, and if the sender marks the resend as a resumed delivery it MUST be ignored by the receiver — which lets the sender pipeline resumes without risking duplication; tags **only the target** considers unsettled MUST be ignored by the sender and MUST be considered settled by the receiver; tags **both** consider unsettled MUST be resumed by the sender.

Resumed transfers set `transfer.resume=true`, and the sender MAY omit message data when the receiver's state shows retransmission is unnecessary — a resumed delivery MAY carry no payload at all and act solely as a vehicle for the sender's terminal state. Receivers MUST ignore resumed deliveries absent from their local unsettled map, senders MUST NOT send resumed transfers for tags absent from theirs, and for a multi-frame resumed delivery `resume` MUST be set on the first transfer. Unsettled tags have no valid delivery-ids until resumed, because the old endpoint's ids are meaningless to the new one [3 §2.6.13, §2.7.5].

`attach.incomplete-unsettled=true` handles maps too large for one frame. While the map is incomplete, absence of a tag is *not* evidence of settlement; a sending endpoint MUST NOT send new (non-resuming) deliveries, and a receiving endpoint that sent an incomplete map MUST detach with an error on receiving a non-resuming transfer. Both ends must reduce unsettled state as far as they can, then suspend and re-attempt the resume; only when both maps are complete may new unsettled state be created, and the endpoints MUST detach and reattach at least once to get there [3 §2.6.3, §2.6.13]. An oversized map not handled this way MAY end the session with `amqp:frame-size-too-small` [3 §2.7.3, §2.8.15]. When *reattaching* rather than resuming, `unsettled` MUST be null; conversely a resuming `attach` MUST have a non-null `unsettled` so it can be distinguished from a pipelined re-attach, receipt of which MUST terminate the session with `amqp:session:errant-link` [3 §2.6.5, §2.7.3].

The design deliberately minimizes stored state: "The original link endpoint state is not necessary for resumption of a link. Only the unsettled delivery state maintained at the termini is necessary... The form of delivery-tags is intentionally left open-ended so that they and their related delivery state can, if desired, be (re)constructed from application state, thereby minimizing or eliminating the need to retain additional protocol-specific state" [3 §2.6]. *Recovering* a link is the extreme case: create an endpoint with an empty source (incoming link) or target (outgoing) and reconstruct everything from the authoritative remote terminus — link name and direction suffice [3 §2.6.3]. If the remote peer has no record either, the returned terminus field is null. Termini properties may also have changed while suspended, in which case the sender holds the authoritative source and the receiver the authoritative target, and either peer may detach if the result is unacceptable [3 §2.6.3].

Part 3 works 14 delivery-tags of resumption cases with concrete states [4 §3.4.6]. The load-bearing ones: a tag the receiver has no record of MUST be resent *without* `resume=true`, since a resumed transfer would be ignored, and if the sender lacks the data it MAY notify the application of possible loss; a tag where the receiver's `received` position precedes the sender's earliest resumable position cannot be completed, and the only option is `aborted=true` plus, if possible, a fresh delivery; where both ends hold the same terminal outcome and neither has settled, the sender SHOULD simply settle; where the outcomes *differ*, the sender's view is definitive because the outcome takes effect at the sender, so the sender MUST restate its outcome and the receiver SHOULD echo it and settle. A sender capable of resuming MUST NOT publish a terminal outcome in its unsettled map until it is sure the receiver will not need the message data resent.

**What an implementation run measured about re-attaching.** After a peer released a link, an `attach` reusing the same link name and carrying **no `unsettled` map** was answered as a new link, and nothing was recovered [67]. That is the specification working as written rather than a limitation: `unsettled` is what distinguishes a *resuming* attach from a re-attach, and "when reattaching, `unsettled` MUST be null" [3 §2.6.13] means an endpoint that reuses a name without the map has asked for a fresh link and has been given one. A client that reconnects, re-attaches by name and expects its in-flight deliveries back has not resumed anything; the resumption machinery starts with the map, and the map starts with unsettled state the terminus kept.

### 6.4 Delivery states and what they mean to a broker

Terminal states are called *outcomes*; one non-terminal state is defined [4 §3.4].

**`received`** (`0x23`; `section-number`, `section-offset`). Non-terminal. At the target, the furthest point that will not need resending; at the source, the earliest point the sender can resume from. `Received(0,0)` means no message data at all was transferred, and `Received(X,N)` for a fully received section X of N bytes is equivalent to `Received(X+1,0)`. It may only appear on the first `transfer` of a resumed delivery, or in an unsettled map [4 §3.4.1].

**`accepted`** (`0x24`). At the target: successfully processed, and the receiver expects the sender to move the delivery to accepted at the source. At the source: retired from the node, and payload transfer can no longer be resumed. Does *not* increment the header `delivery-count`. A delivery may become accepted at the source before all transfer frames are sent, which does not imply the rest will not be sent — only `aborted` signals premature termination [4 §3.4.2]. Broker meaning: consumed. RabbitMQ deletes the queued message; as a receiver, `accepted` means every routed queue accepted the transfer, and for a quorum queue that a majority wrote it to disk [14]. Service Bus removes the message [57]. Artemis performs an individual broker acknowledgement [54].

**`released`** (`0x26`). No longer acquired by the receiver, made available for redelivery to the same or other targets, message *unchanged* — `delivery-count` MUST NOT be incremented. The source MAY attain it spontaneously, for example when a time-bound acquisition lock is revoked. At the target it means the transfer was not and will not be acted upon [4 §3.4.4]. Broker meaning: requeue, no penalty. RabbitMQ requeues for the same or a different consumer, and as a receiver `released` means no queue could be routed to [14]. Service Bus documents `released` as the AMQP representation of abandon [57]. Artemis cancels with `failure=false` [54]. Dispatch uses `released` for a delivery that reached no destination [26 §11.1.1].

**`rejected`** (`0x25`; optional `error`). At the target: invalid and unprocessable; applying it *does* increment the header `delivery-count`. At the source it means the target said so and the source acted; a delivery "SHOULD NOT ever spontaneously attain the rejected state at the source" [4 §3.4.3]. Broker meaning: dead. RabbitMQ dead-letters the message, or drops it with no dead-letter configuration; as a receiver it returns `rejected` for a queue-length rejection (`reason=maxlen`), an unavailable classic queue (`reason=unavailable`) or an invalid anonymous-terminus address, with `queue` and `reason` in the error info map [14]. Service Bus retains the message for another receiver on `rejected` or `released` and dead-letters it once repeated rejects/releases reach the entity's maximum delivery count [57]. Artemis takes the rejection path unless `amqpTreatRejectAsUnmodifiedDeliveryFailed=true` (source default `false`) makes it cancel with `failure=true` [54].

**`modified`** (`0x27`; `delivery-failed`, `undeliverable-here`, `message-annotations`). Like released but with recorded changes. `delivery-failed=true` MUST increment `delivery-count`; `undeliverable-here=true` means the message MUST NOT be redelivered to the modifying link endpoint; the annotations map is merged into the message's existing message-annotations, values in the outcome replacing existing keys. The source MAY attain it spontaneously, e.g. to mark a revoked lock as a failed attempt [4 §3.4.5]. Broker meaning: requeue with a note. RabbitMQ supports annotation changes on quorum queues but not classic queues, and calls modifying a stream message unsuitable because streams are immutable; `undeliverable-here=true` dead-letters or drops and `false` requeues, with the guide warning the `true` behaviour may change, and requeuing a quorum-queue message always increments the `x-delivery-count` annotation [14; 17]. Artemis marks the current consumer as rejected for that message on `undeliverable-here=true` and cancels with `failure=true` on `delivery-failed=true` (else false), after which normal redelivery and dead-letter settings apply [54; 49]. Service Bus "does not use modified at present" [57].

**Default outcome and node states.** `source.default-outcome` is the outcome applied to transfers that have not reached a terminal state at the receiver when the transfer is settled, including when the source is destroyed. `source.outcomes` lists the symbolic descriptors the link may choose from; it may be empty, meaning `default-outcome` is assumed for everything, and if neither is set the source MUST support `accepted` [4 §3.5.3]. Part 3's distribution-node state machine ties them together: a message is AVAILABLE, moves to ACQUIRED before an acquiring transfer (and is then ineligible for acquiring transfers on any other link), stays ACQUIRED until the transfer settles, then goes to ARCHIVED on `accepted`/`rejected` or back to AVAILABLE on `released`/`modified`. If the receiver's state is unknown — the link endpoint was destroyed before recovery — `default-outcome` decides. Spontaneous transitions happen too: a TTL expiry can move a message from AVAILABLE to ARCHIVED, transitioning any transfers to a terminal outcome at the node regardless of receiver state. The state of a message at one distribution node does not affect its state at another [4 §3.3].

### 6.5 Persistence

Two orthogonal knobs. **Message durability**: `header.durable=true` demands that the message "MUST NOT be lost even if an intermediary is unexpectedly terminated and restarted", and a target that cannot honour it MUST NOT accept it, rejecting with `amqp:precondition-failed` or detaching with the same error [4 §3.2.1]. Per message, and a hard contract rather than a preference. **Terminus durability**: `source.durable`/`target.durable` (default `none`) is `none` (0, no terminus state retained), `configuration` (1, only existence and configuration) or `unsettled-state` (2, those plus the unsettled state for durable messages) [4 §3.5.5]. `unsettled-state` is what makes exactly-once survive a broker restart, since it is the unsettled map that resumption compares. `expiry-policy` (default `session-end`) decides when the `timeout` countdown starts — `link-detach`, `session-end`, `connection-close`, `never` — with re-attaching before expiry aborting the countdown and a recurrence restarting the timer from the full configured value; `timeout` is in seconds, default 0 [4 §3.5.3-3.5.6].

**What the acknowledgement certifies.** A `disposition` with `state=accepted` from a receiver certifies that *that receiver* processed the message; it says nothing about disk. Durability is asserted by `header.durable` on the way in, enforced by the target's refusal to accept otherwise, and retained per `terminus-durability` [4 §3.2.1, §3.4.2, §3.5.5]. Implementations sharpen it — RabbitMQ's `accepted` from a quorum queue means a majority wrote the message to disk [14]. Support for the durability machinery is uneven. RabbitMQ explicitly does not support link suspend/resume, resumed deliveries, exactly-once delivery, or the terminus expiry policy [14 "Limitations"]. Service Bus does not support link recovery: "if a connection is lost with an unsettled transfer pending, that transfer is lost", the client must reconnect, reattach and retry, and consequently Service Bus and Event Hubs document at-least-once rather than AMQP-level exactly-once, offering optional `message-id` duplicate detection over a configured window instead [57]. Artemis forces `rcv-settle-mode=first`, its own test commenting "The Broker does not currently support ReceiverSettleMode of SECOND" [54]. The reviewed Proton 0.40.0 and Dispatch 1.19.0 documentation describes no automatic resumption or unsettled-map recovery either; Dispatch says a broker connection failure detaches routed links and the client must be configured to reattach [30; 31; 26 §11.2.2].

### 6.6 Transactions as an acknowledgement mechanism

Part 4 exists to coordinate the outcomes of otherwise independent transfers "across any number of distinct links in either direction" [5 §4.1]. The controller attaches a control link to a `coordinator` target, sends a message whose body is a single `amqp-value` holding `declare` (optionally with `global-id`, which requires the `amqp:distributed-transactions` capability), and receives `disposition(state=declared(txn-id))`. Neither `declare` nor `discharge` may be sent settled — the sender must see the outcome — and a coordinator receiving a pre-settled one SHOULD detach with `amqp:illegal-state`. Errors come back as `rejected` carrying a `transaction-error`, or, if the source does not support `rejected`, as a `detach` carrying it; controllers SHOULD therefore establish a control link that allows `rejected` [5 §4.2-4.3, §4.5.2].

Transactional work is exactly three operations: *posting* a message at a target (making it available), *acquiring* a message at a source, and *retiring* a message at a source by applying its terminal outcome. They are triggered by incoming `transfer`, `flow` and `disposition` frames respectively, each tagged with `transactional-state(txn-id, outcome)` [5 §4.4]. Posting: the message does not become available at the destination until discharge succeeds; every frame of a multi-frame delivery MUST carry the same transaction, and discharging while a partial delivery is outstanding MUST terminate the control link with `amqp:transaction:rollback`. On receiving an unsettled transactional delivery the resource MUST inform the controller of the presumptive terminal outcome before it can discharge [5 §4.4.1]. Retirement: the controller sends `disposition(state=transactional-state(txn-id, outcome=accepted))` covering a delivery range; on successful discharge the outcome is applied and the transfers may be settled immediately, while on rollback the outcome is not applied and the deliveries stay live and acquired by the controller [5 §4.4.2]. Acquisition: the controller puts `txn-id` in `flow.properties`, setting a per-link-endpoint txn-id under which acquired messages are associated; the txn-id is cleared on discharge but the *credit* is not, so the controller SHOULD drive credit to zero or set drain before discharging to avoid acquiring outside a transaction. A link endpoint not supporting transactional acquisition MUST be terminated with `amqp:not-implemented` [5 §4.4.3].

`discharge(txn-id, fail)` commits when `fail` is false and rolls back when true; a coordinator MUST always be able to complete a `discharge` with `fail=true`, since coordinator failure means rollback anyway [5 §4.3, §4.5.3]. Closing the control link while non-discharged transactions exist immediately rolls them all back [5 §4.1]. Coordinator capabilities: `amqp:local-transactions`, `amqp:distributed-transactions`, `amqp:promotable-transactions`, `amqp:multi-txns-per-ssn`, `amqp:multi-ssns-per-txn` [5 §4.5.7]. Errors: `amqp:transaction:unknown-id`, `amqp:transaction:rollback`, `amqp:transaction:timeout` [5 §4.5.8]. Distributed transactions are deferred to "a separate specification" / "Part 6 Distributed Transactions", which was never published [5 §4.5.2-4.5.3].

Broker reality: Artemis supports a coordinator target, makes the underlying server session transacted and commits or rolls back through it, but supports only a *single transaction per session* despite `amqp:multi-txns-per-ssn` existing; its resource manager `transaction-timeout` default is `300000` ms with a `1000` ms scan period, and prepared XA transactions are not rolled back automatically — management must do so heuristically [41; 47; 52]. Dispatch states that AMQP 1.0 does not specify XA details and it does not support XA; it supports local transactions to *one* broker via a `$coordinator` link route, and all transaction links must route to that broker [26 §§1.2, 11.2.2]. RabbitMQ does not support AMQP 1.0 transactions at all [14].

## 7. Ordering and duplicates

**What is ordered.** The connection: "if the nth frame arrives, all frames prior to n MUST also have arrived" [3 §2.1.2]. The session: a bidirectional *sequential* conversation with a shared delivery-id sequence [3 §2.5]. Within one link, deliveries MUST NOT interleave, so a multi-frame message arrives contiguously [3 §2.6.14]. That is the whole promise.

**What is not.** Nothing guarantees relative order *between* links, even on one session — deliveries on different links may interleave arbitrarily [3 §2.6.14]. Nothing guarantees order between sessions on a connection: channels are independent frame sequences multiplexed into one, and the spec says sessions on a connection are independent while links on a session are not [3 §2.1.2, §2.5]. `header.priority` explicitly permits reordering: "Messages with higher priorities MAY be delivered before those with lower priorities" [4 §3.2.1]. `copy` distribution and multicast fan-out say nothing about relative order across the resulting links, and redelivery after `released`/`modified` returns a message to AVAILABLE with no positional guarantee [4 §3.3, §3.4.4-3.4.5]. There is no partition or key-ordering concept; `group-id`/`group-sequence` let an application express grouping and relative position but carry no protocol ordering semantics [4 §3.2.4].

**Broker-level ordering.** RabbitMQ says that for a single active consumer, stopping the link and acknowledging before detach — or detaching directly, which requeues unacknowledged transfers — activates the next consumer, which receives messages in original order; for quorum queues it reports `rabbitmq:active` as a boolean in `flow.properties` after initial credit and whenever SAC activity changes [16; 14]. Matching stream consumption with filters preserves order among each consumer's matching messages [19]. Dispatch's `balanced` distribution deliberately spreads across receivers and therefore preserves no single order [26 §11.1.2].

**Where duplicates arise.** Three places, all named by the spec. (1) At-least-once by construction: the receiver settles before the sender, and a lost `disposition` makes the sender resend on resumption, "resulting in duplicate processing of the message at the receiver" [3 §2.6.12]. (2) The general rule: "if the receiver settles prior to the sender, it is possible for duplicate messages to occur, except in the case where the sender settles before the initial transmission" [3 §2.6.12]. (3) Resumption ambiguity: a tag the receiver has no record of MUST be resent to preserve at-least-once or exactly-once, and the sender cannot know whether the receiver processed and forgot it [4 §3.4.6, tags 1 and 5]. Redelivery after `released`/`modified` is also a duplicate from an at-least-once consumer's viewpoint; the protocol does not call it one because the message was never accepted.

**What the protocol offers to detect them.** Four things. `header.delivery-count`, the number of prior *unsuccessful* attempts — zero on first delivery, incremented by `rejected` and `modified{delivery-failed=true}` but not by `accepted` or `released` — where "if this value is non-zero it can be taken as an indication that the delivery might be a duplicate" [4 §3.2.1, §3.4.2-3.4.5]. `header.first-acquirer`, true meaning the message has not been acquired by any other link [4 §3.2.1]. `properties.message-id`, with explicit authorization for a broker to discard a duplicate whose message-id matches a previously received message sent to the same node [4 §3.2.4]. And the `rcv-settle-mode=second` handshake plus link resumption, the only mechanism that actually *suppresses* duplicates rather than flagging them, because it stops the receiver forgetting a tag before the sender does — the spec names the dedup set explicitly: on learning of remote settlement the receiving application can "remove the delivery-tag from a set kept for de-duplication" [3 §2.6.12].

**Broker deduplication.** Artemis: `amqpDuplicateDetection` defaults to `true` in the current protocol manager source, making the receiver's routing context use duplicate detection; the duplicate-ID property is `_AMQ_DUPL_ID`, looked up in application properties, backed by a fixed-size circular cache per address with `id-cache-size` default `20000` (0 disables) and `persist-id-cache` default `true` [48; 54]. Service Bus offers optional duplicate detection on `message-id` over a configured window and presents it as the substitute for the AMQP exactly-once machinery it does not implement [57].

## 9. Reliability recipes

**Idle-timeout keep-alive.** *Problem:* a dead peer holds resources indefinitely and TCP alone may not notice. *Mechanism:* advertise `open.idle-time-out`; when there is nothing to send, emit an empty frame (header only) or a `flow` for a valid session. *Guarantee:* liveness detection within the advertised interval. *Cost:* one frame per interval per idle connection, and since the advertised value SHOULD be half the local threshold, twice the minimum traffic. *Failure modes:* a heavily loaded peer trips its partner's timeout, which is why such a peer SHOULD proactively close with an explanation; and a peer advertising nothing may still be reaped by an internal default [3 §2.4.5]. Artemis sends `amqpIdleTimeout / 2` in its `open`, so 60000 tells the client to send every 30000 ms, while `amqpIdleTimeout=0` tells clients not to send keep-alives and leaves closure to TCP; its documentation states no default, and the general Core `connectionTTL` default is `60000` ms with `connection-ttl-override` `-1` and a `2000` ms check interval [41; 52; 53]. Dispatch defaults `idleTimeoutSeconds` to 16 on both `listener` and `connector` [27].

**Prefetch tuning.** *Problem:* one-message-at-a-time round trips waste latency, while unbounded push overruns the consumer and can expire locks. *Mechanism:* the spec's own asynchronous-notification pattern — pick a target `link-credit` and top up when the sender's credit falls below a threshold [3 §2.6.9]. *Guarantee:* the incoming rate is bounded by how fast the receiver advances the delivery-limit. *Cost:* memory for prefetched messages at the consumer plus messages held ACQUIRED at the node. *Failure modes:* Service Bus names the sharpest — the lock clock starts when the message leaves the entity, not when it hits the wire, so excessive credit can expire a lock before the application sees the message [57]. Concrete tunings: Artemis `amqpCredits=1000`/`amqpLowCredits=300` [41; 54]; Classic `transport.producerCredit` and `transport.prefetch`, consumer default 1000 when the client sets none [56]; RabbitMQ's publisher-side 170 with a low-water mark of 85 [16]; legacy Service Bus `PrefetchCount` default `0` [61].

**Stopping and draining a link.** *Problem:* a consumer needs to know when no further transfer can arrive, for handover, shutdown, or a synchronous get with a timeout. *Mechanism:* `flow(link-credit=0, echo=true)` and wait for the echoed `flow`, or `flow(drain=true)` and wait for credit to reach zero. *Guarantee:* a definite quiescence point; drain additionally distinguishes "a message arrived" from "there was none". *Cost:* one extra round trip. *Failure modes:* in-flight transfers still arrive until the sender processes the new state, and answering echo with echo loops forever [3 §2.6.8, §2.6.10, §2.7.4]. RabbitMQ documents the credit-zero-plus-echo sequence for pausing a consumer, and notes that for a single active consumer stopping and acknowledging before detach hands over cleanly whereas detaching directly requeues unacknowledged transfers [16].

**Transactions for atomic consume-and-produce.** *Problem:* a worker consumes from one node and produces to another and must not do half the job. *Mechanism:* declare a transaction on a control link to a `coordinator`; tag both the outgoing `transfer` and the incoming delivery's `disposition` with `transactional-state(txn-id, ...)`; discharge with `fail=false`. Posted messages do not become available and retirement outcomes are not applied until discharge succeeds [5 §4.4.1-4.4.2]. *Guarantee:* a coordinated outcome across any number of transfers on any number of links in either direction [5 §4.1]. *Cost:* a control link, a round trip per declare and per discharge, resource-side state per open transaction, and the discipline of driving credit to zero before discharging if transactional acquisition is in use [5 §4.4.3]. *Failure modes:* discharging with a partial delivery outstanding kills the control link with `amqp:transaction:rollback` [5 §4.4.1]; `amqp:transaction:timeout` if the work takes too long [5 §4.5.8]; distributed transactions were never specified [5 §4.5.2]; Artemis allows one transaction per session [41]; Dispatch cannot route a transaction to more than one broker [26 §11.2.2]; RabbitMQ does not implement Part 4 [14].

**Dead-lettering via `rejected` or `modified`.** *Problem:* a poison message must not loop forever. *Mechanism:* answer `rejected(error=...)` for "invalid and unprocessable", or `modified(delivery-failed=true, undeliverable-here=true, message-annotations={...})` to requeue with a note and keep it away from this consumer. Both increment the header `delivery-count` — rejected always, modified when `delivery-failed` — which is what a redelivery limit counts [4 §3.4.3, §3.4.5]. *Guarantee:* a bounded number of attempts, plus diagnostic information carried on the message. *Cost:* annotation growth and a broker-specific dead-letter destination the protocol does not define. *Failure modes:* semantics diverge. RabbitMQ treats consumer `rejected` as dead-letter-or-drop and `modified{undeliverable-here=true}` likewise, warns the latter may change, and supports annotation changes only on quorum queues [14; 17]. Artemis routes through `dead-letter-address` after `max-delivery-attempts` (documented as 10 by default, `-1` for infinite), with `redelivery-delay` default `0`, `redelivery-delay-multiplier` `1.0`, `redelivery-collision-avoidance-factor` `0.0` and `max-redelivery-delay` defaulting to `redelivery-delay * 10`, and copies the message adding `x-opt-ORIG-MESSAGE-ID`, `x-opt-ACTUAL-EXPIRY`, `x-opt-ORIG-QUEUE`, `x-opt-ORIG-ADDRESS` [49; 44; 41]. Service Bus dead-letters after repeated rejects/releases reach the entity maximum and does not use `modified` [57]. Dispatch recommends link routing over message routing when `modified{undeliverable-here=true}` semantics matter, because message routing hides the broker from the consumer [26 §11.1.3].

**Link recovery.** *Problem:* a connection dies mid-flight and neither side knows what the other did. *Mechanism:* durable termini (`terminus-durability=unsettled-state`, with `expiry-policy`/`timeout` long enough to survive the outage), a stable `container-id`, stable link names, and a resuming `attach` carrying the local unsettled map; then the three-way comparison and the 14 concrete cases [3 §2.6.3, §2.6.13; 4 §3.4.6, §3.5.5]. *Guarantee:* the only path to genuine exactly-once in this protocol. *Cost:* durable unsettled state at both termini, `attach` frames that may not fit in one frame (hence `incomplete-unsettled` and the mandatory detach/reattach cycle), and application-visible delivery-tag management. *Failure modes:* an incomplete unsettled map forbids new deliveries until both maps are complete [3 §2.6.3]; a receiver whose `received` position precedes the sender's earliest resumable position forces an `aborted` transfer and a fresh delivery [4 §3.4.6 tag 7]; links to a coordinator cannot be resumed [5 §4.2]; and support is thin — RabbitMQ lists link suspend/resume, resumed deliveries and exactly-once as unsupported [14], Service Bus supports no link recovery [57], and Dispatch's `router.allowResumableLinkRoute` (default `True`) only permits routed links whose terminus timeout is non-zero or whose expiry policy is not `link-detach`, a policy gate rather than automatic recovery [27; 26 §11.2.2].

**Redirect-driven failover.** *Problem:* a container moves. *Mechanism:* `amqp:connection:redirect` or `amqp:link:redirect` with `hostname`, `network-host`, `port` and, for links, `address`; over WebSocket also `scheme` and `path` [3 §2.8.16, §2.8.18; 8 §3]. *Guarantee:* the client is told where to go. *Cost:* a round trip and a reconnect. *Failure modes:* no retry limit, loop detection or backoff is specified, and the WSB spec has to add the rule that a `wss` connection SHOULD NOT be redirected to `ws` [8 §3.1].

**Router mesh instead of a broker.** *Problem:* store-and-forward brokers add latency, disk and a failover problem. *Mechanism:* a Dispatch/Skupper mesh routing messages or links without taking ownership, propagating settlement and disposition end-to-end, with interior routers using link-state routing and recovering via redundant paths rather than clustering [29; 26 §2.2, §§4-5]. *Guarantee:* end-to-end reliability with no persistent store — the router never claims to have stored anything. *Cost:* no buffering, so producers block when consumers are absent, and a broker is still required whenever store-and-forward is genuinely needed [26 §2.2, §11.1.1]. *Failure modes:* on route-container connection loss a transfer may return `RELEASED` or `MODIFIED` and the client must resend [26 §11.1.3]; and Dispatch 1.19.0 is retired, with no new features, fixes or security updates [26].

## 10. Security and identity

**Authentication mechanisms.** SASL per RFC 4422, in type-`0x01` frames with a fixed 512-octet frame cap. The server advertises `sasl-server-mechanisms` in decreasing preference; the client MUST authenticate "using the highest-level security profile it can handle from the list provided by the partner"; an unsupported mechanism means the server "MUST close the connection with the authentication-failure close-code". The spec mandates no mechanism; it normatively references PLAIN (RFC 4616), SCRAM (RFC 5802) and ANONYMOUS-by-convention without requiring any [1; 6 §5.3]. TLS client certificates authenticate at the TLS layer, and the SNI value can select both the back end and the domain against which to validate client credentials [6 §5.2].

Broker-offered mechanisms: Artemis documents exactly `PLAIN`, `ANONYMOUS` and `GSSAPI`, with a `saslMechanisms` acceptor parameter and `saslLoginConfigScope` default `amqp-sasl-gssapi`, and does not document `EXTERNAL` [41; 54]. RabbitMQ requires SASL on AMQP 1.0 and rejects the connection without it, documenting username/password via its authentication backends, JWT (OAuth 2), and x.509 via SASL `EXTERNAL` with `rabbitmq_auth_mechanism_ssl` [14]. Service Bus supports SASL PLAIN with the Shared Access rule name as username and the base64 key as password, plus SASL ANONYMOUS to defer authorization to CBS, and requires TLS before SASL [57]. Classic "accepts plain SASL authentication" [56].

**Claims-based security.** Not in the core standard, and two incompatible shapes exist. OASIS CBS CSD 01 (17 March 2021) defines a connection-scoped token cache, default node address `$cbs`, capability `AMQP_CBS_V1_0`, an optional `cbs-node` connection property, a `set-token` message with `subject`=`set-token` and optional `application-properties.token-type`, success signalled by the ordinary `accepted`/`rejected` disposition, an `AMQPCBS` SASL mechanism for seeding the cache, and a mandatory 8192-octet maximum SASL frame size; standard token type names are `amqp:`-prefixed, JWT being `amqp:jwt` [11 §§2-4]. Service Bus instead uses a request/response link pair to `$cbs` with `application-properties` keys `operation` (=`put-token`), `type`, `name` (the entity path as audience) and optional `expiration`, with token types `jwt` and `servicebus.windows.net:sastoken`; a valid `put-token` must succeed for an entity within 20 seconds of connection establishment or Service Bus drops the connection, at token expiry it promptly drops that entity's links, and refresh is another `put-token`. Its current implementation permits CBS only with SASL `ANONYMOUS` [57].

**Authorization model.** The core standard has none. It supplies the error conditions (`amqp:unauthorized-access`, `amqp:not-allowed`, `amqp:resource-locked`) and a place to refuse — `attach` with a null terminus, or `detach(error=...)` — and stops [3 §2.6.3, §2.8.15]. Broker granularity: Artemis authorizes per address by exact match or wildcard with permissions `createAddress`, durable and non-durable queue create/delete, `send`, `consume`, `browse`, `manage`, and a fully qualified queue name can further restrict consumption and browsing but cannot constrain a send to the address as a whole [46]. RabbitMQ scopes by virtual host selected through `open.hostname` — a client picks a non-default vhost by setting it to e.g. `vhost:tenant-1`, not by prefixing the address; `default_vhost = /`, and target `/queues/:queue` routes internally through `amq.default` and therefore needs write permission on it [14]. Service Bus rights are `Send`, `Listen` and `Manage`, with sender links requiring Send and receiver links Listen [57]. Classic applies its authorization policies when a destination is accessed for read or write [56].

**Does identity travel with a message?** One field: `properties.user-id`, "the identity of the user responsible for producing the message", client-set and which "MAY be authenticated by intermediaries" [4 §3.2.4]. It is part of the bare message and therefore immutable, so an intermediary can verify but not rewrite it. Nothing else carries an authenticated principal, and there is no signature mechanism in the core standard — though `footer` exists precisely to hold "message hashes, HMACs, signatures and encryption details" computed over the immutable bare message, and the immutability rule exists to keep them valid [4 §3.2, §3.2.9]. The connection endpoint diagram lists `principal` as connection state [3 Figure 2.9], but no performative field carries it.

**Transport security.** TLS as a protocol-id-2 layer with in-band upgrade, or as a pure TLS listener on 5671 [6 §5.2, §5.2.1]. The TLS client MUST validate the server certificate and SHOULD use SNI; unidirectional shutdown is permitted. TLS 1.2 (RFC 5246) is the normatively referenced version — the standard predates 1.3 [1; 6 §5.2]. Layers nest, so SASL may run inside TLS. Over WebSocket, `wss` provides transport security and the binding explicitly does not support SASL mechanisms that themselves provide encryption [8 §2.2]. Service Bus requires TLS on every path: 5671 is TLS-first, 5672 mandates an AMQP TLS upgrade, and WebSockets on 443 is equivalent to a 5671 connection [57].

**What the extensions raise.** Filter Expressions flags complex expressions (compute exhaustion), induced errors and injection as attack surfaces [9 §7]. The Addressing draft motivates its scope model with air-gapped networks: routing application-level messages across isolated IP networks without exposing IP-level access, with optional masquerading of traffic origins so a receiver cannot discover the routing topology [10 §2].

**What an unbounded resource looks like.** The defaults are the answer: a peer accepting them has agreed to a single frame of up to 4 GiB, 65536 concurrent sessions, 2^32 links per session, messages of unbounded size, and a connection that never times out. Only three limits are safe by construction, because they are mandatory (`incoming-window`, `outgoing-window`) or start closed (`link-credit` = 0) [3 §2.6.7, §2.7.2]. The unsettled map is the other unbounded structure: it grows with in-flight deliveries and, for a durable terminus, persists across restarts, and the spec's only defence is `incomplete-unsettled`, which bounds the frame but not the map [3 §2.6.3, §2.7.3]. Link names are "arbitrarily long without a significant penalty" [3 §2.6.1]. `application-properties` restricts values to simple types, excluding maps, lists and arrays, which bounds nesting there but not in annotations or the body [4 §3.2.5]. Filter Expressions adds compute exhaustion via complex expressions [9 §7.1].

**Broker-configured limits.**

## 12. Answers to the problem catalogue

**P1 — Loss detection and safe retry.** Detection is by absence of a `disposition`: a delivery sent unsettled stays in the sender's unsettled map until the receiver reports a terminal state and the sender settles [3 §2.6.12]. Retry is made safe by *link resumption* rather than by timeout: on re-attach both ends publish their unsettled maps and the three-way rule decides — tags only the sender holds MAY be resumed (and if flagged `resume=true` are ignored, so pipelining is safe), tags only the receiver holds MUST be ignored by the sender and treated as settled by the receiver, tags both hold MUST be resumed [3 §2.6.13]. A tag the receiver has no record of MUST be resent *without* `resume`, which is the duplicate-admitting case [4 §3.4.6]. Idempotency support: `header.delivery-count`, `header.first-acquirer`, and explicit authorization for a broker to discard a duplicate `properties.message-id` sent to the same node [4 §3.2.1, §3.2.4]. Where resumption is absent — Service Bus, RabbitMQ — retry means reconnect, reattach and resend, i.e. at-least-once with broker-side `message-id` deduplication as the substitute [57; 14].

**P2 — Liveness, timing, state of a dead peer.** `open.idle-time-out` in milliseconds, per direction and independent; the advertised value SHOULD be half the local threshold, and a peer with nothing to send emits an empty frame or a `flow`. On expiry, close with an error, then optionally drop the socket; TCP keep-alive is recommended alongside [3 §2.4.5]. There is no last will and no session-takeover concept. What survives is decided by the terminus: `expiry-policy` (`link-detach`, `session-end`, `connection-close`, `never`) starts a `timeout` countdown, `durable` decides what is kept (`none`, `configuration`, `unsettled-state`), and re-attaching before expiry aborts the countdown [4 §3.5.3-3.5.6]. In-flight deliveries whose state at the receiver is unknown get `source.default-outcome` [4 §3.3]. Concrete timings: Dispatch `idleTimeoutSeconds` 16 [27]; Artemis advertises `amqpIdleTimeout / 2` [41]; Service Bus drops a connection whose entity has no valid CBS token within 20 seconds [57].

**P3 — Spreading work by capacity, not turn.** Link credit. Each receiver independently advertises its own `link-credit` on its own link, and the sender may only advance `delivery-count` up to `delivery-count + link-credit` [3 §2.6.7]; a fast worker replenishes sooner and therefore receives more, and the unit is one message. The node side is `distribution-mode=move`, which moves a message to ACQUIRED and makes it ineligible for acquiring transfers on any other link, so competing consumers do not double-take [4 §3.3, §3.5.2]. Broker vocabulary: Artemis `ANYCAST` [43]; Dispatch `balanced`, which "delivers to one receiver and balances according to rate of settlement" — capacity, not turn — versus `closest`, which is nearest-only [26 §11.1.2; 27].

**P4 — Slow consumer.** The backlog sits at the sending node, and the sender tells the receiver its size: `flow.available` is "the number of messages awaiting credit at the link sender endpoint" [3 §2.6.7]. The bound is `link-credit` for messages in flight per link and the session `incoming-window` for transfer frames in flight per session. At the bound the sender **blocks**: "If the link-credit is less than or equal to zero... a sender MUST NOT send more messages" — no drop, no disconnect, no error [3 §2.6.7]. The only error variants are optional and punish the peer that broke the rules: `amqp:link:transfer-limit-exceeded` if the receiver chooses to punish transfers arriving after it cut credit, and `amqp:session:window-violation` for exceeding the session window [3 §2.6.7, §2.8.17]. Brokers propagate the block to publishers by withholding credit: RabbitMQ stops granting on the specific publisher link whose target queue is slow, and sends `incoming_window = 0` on every session during a memory or disk alarm [16]; Artemis stops issuing producer credit under `address-full-policy=BLOCK`, with `max-size-bytes-reject-threshold` as a hard reject because credit counts messages not bytes, and offers `PAGE` (default), `DROP` and `FAIL` as alternatives [42; 44]; Dispatch grants producer credit only while a consumer exists, since it stores nothing [26 §11.1.1].

**P5 — Late joiner needing current state.** No answer in the core protocol. There is no last-value, retained-message, snapshot or replay concept: a source transfers messages meeting its entry criteria and MUST NOT resend a message already transferred to an ACCEPTED state [4 §3.5.2]. The nearest primitives are `distribution-mode=copy`, which leaves node state unchanged so several links can each receive the same message [4 §3.5.2, §3.5.7], and `source.filter`, which restricts what a newly attached link admits [4 §3.5.1]. Replay is a broker feature reached through filters: RabbitMQ streams support AMQP filter expressions and offset/Bloom filtering to consume from a position [14; 19]; Service Bus exposes `com.microsoft:peek-message` with a `from-sequence-number` and `com.microsoft:receive-by-sequence-number` over `$management` [58].

**P6 — Failover to another broker.** Protocol-level: `amqp:connection:redirect` and `amqp:link:redirect` carry `hostname`, `network-host`, `port` and, for links, `address`, with `scheme` and `path` added over WebSocket [3 §2.8.16, §2.8.18; 8 §3]. Nothing is re-established automatically. What *can* be re-established explicitly is a link, by name, against surviving termini — subscriptions and unsettled deliveries included, if `terminus-durability` and `expiry-policy` allowed them to survive [3 §2.6.3, §2.6.13; 4 §3.5.5] — and the `container-id` must match across the reconnect [10 §2.4]. Recovery is possible even from near-total local state loss: link name and direction suffice, and the remote terminus supplies the rest [3 §2.6.3]. In practice: Dispatch interior routers recover via redundant paths rather than clustering, but a broker connection loss detaches routed links and the client must reattach [26 §§4-5, §11.2.2]; Service Bus has no link recovery and the client must reconnect, reattach and retry [57].

**P7 — Surviving a restart.** Persisted: whatever `terminus-durability` says — nothing, terminus existence and configuration, or those plus the unsettled state for durable messages [4 §3.5.5]. Which messages are durable is decided per message by the *sender* via `header.durable`, and the target has no discretion to accept and then lose one: it MUST refuse with `amqp:precondition-failed` if it cannot honour the demand [4 §3.2.1]. Terminus attributes are requested by the attaching peer and reported as actually created by the other [3 §2.6.3]. The certifying acknowledgement is `disposition(state=accepted)` from the receiver, which the spec defines as "successfully processed" and which does not itself mean "on disk"; durability comes from the `durable` contract, not the outcome [4 §3.2.1, §3.4.2]. Implementations sharpen it: RabbitMQ's `accepted` from a quorum queue means a majority wrote the message to disk [14].

**P8 — Ordering and scope.** Connection: frames arrive in order with no gaps [3 §2.1.2]. Session: a sequential conversation with a shared delivery-id sequence [3 §2.5]. Link: deliveries MUST NOT interleave, so a message's frames are contiguous [3 §2.6.14]. Nothing is promised across links, across sessions, or per key or partition — there is no partition concept. `header.priority` explicitly licenses reordering [4 §3.2.1], and redelivery after `released`/`modified` returns the message to AVAILABLE with no positional guarantee [4 §3.3]. `group-id`/`group-sequence` express grouping without protocol ordering semantics [4 §3.2.4]. Broker additions: RabbitMQ preserves original order on single-active-consumer handover and among a stream consumer's matching messages [16; 19]; Dispatch `balanced` deliberately does not [26 §11.1.2].

**P9 — Duplicates and what "exactly once" means.** Duplicates arise when the receiver settles before the sender (unless the sender settled before the initial transmission), specifically when a receiver's terminal `disposition` is lost and the sender resends on resumption [3 §2.6.12], and from resumption ambiguity, since a tag the receiver does not remember MUST be resent [4 §3.4.6]. "Exactly once" here is a precise construction, not a mode name: `snd-settle-mode=unsettled` plus `rcv-settle-mode=second`, where the sender settles only after the receiver reaches a terminal state and the receiver settles only after learning the sender settled — plus link resumption to resolve the in-doubt set after a failure, plus a terminus durable enough to make resumption possible [3 §2.6.12-2.6.13; 4 §3.5.5]. Suppression is the receiver keeping the tag in its dedup set until the sender's settlement arrives [3 §2.6.12]; weaker suppression is broker discard on `properties.message-id` [4 §3.2.4]. Support is the exception: RabbitMQ lists exactly-once as unsupported [14], Artemis forces `rcv-settle-mode=first` [54], and Service Bus documents at-least-once with optional `message-id` duplicate detection instead [57].

**P10 — Request/reply correlation and routing back.** `properties.reply-to` names the reply node, `correlation-id` ties response to request, `reply-to-group-id` routes replies to a group [4 §3.2.4]; both are in the immutable bare message so intermediaries cannot rewrite them. The reply node is commonly created on demand: the requester sets `source.dynamic=true`, the peer creates the node and returns its address, and `lifetime-policy=delete-on-close` ties it to the link [4 §3.5.3, §3.5.9-3.5.10]. Routing back through intermediaries: recipients and intermediaries SHOULD prioritize replying over the connection the request arrived on and only then fall back to an outbound connection to the `reply-to` network endpoint, while any network endpoint in a *link* address MUST be ignored [10 §3.2.1, §3.2.3]. The JMS mapping is direct: `JMSReplyTo` to `reply-to`, `JMSCorrelationID` to `correlation-id` [13 §§3.2.1, 5.1]. Service Bus's `$management`/`$cbs` and the Management draft build request/response out of exactly these fields plus a `statusCode` application property [57; 58; 12].

**P11 — Topology, binding, discovery.** Symmetric by design: "AMQP does not differentiate between clients and servers, but only knows communicating peers" [10 §2.1]. Either peer may initiate `attach` in either role, and the transport spec uses "client" and "server" only for TCP roles [3 §2.6.3]. The only asymmetries are TCP-level — the TCP client sends its header first, the TLS client is the TCP client, the SASL client is the TCP client — plus the convention that the peer holding addressable nodes resolves addresses [3 §2.2; 6 §5.2-5.3]. Brokered and brokerless are both native: a broker is just a container holding distribution nodes, and Dispatch demonstrates the brokerless case — a router that "never assumes ownership of a message" and still delivers end-to-end guarantees, needing a broker only for store-and-forward [3 §2.1.1; 29; 26 §2.2]. Discovery: none in the core standard; `redirect` errors point elsewhere after the fact [3 §2.8.16, §2.8.18]. The Addressing draft adds scope identifiers following DNS naming conventions but explicitly not requiring DNS registration or IP addresses, plus "on-ramp" containers as IP-addressable entry points into an overlay, and leaves scope-to-container resolution unspecified [10 §2.3, §3.2].

**P12 — Flow-control credit.** Two schemes. Link: unit one message, grantor the receiver alone, default 0 at attach, exhaustion means the sender MUST NOT send more, i.e. blocks [3 §2.6.7]. Session: unit one transfer frame (byte control in disguise, since frames are size-capped), grantor the receiver of that direction via `incoming-window`, no default because the field is mandatory on `begin`, exhaustion means the sender must stop and violating it MUST end the session with `amqp:session:window-violation` [3 §2.5.6, §2.7.2, §2.8.17]. No per-connection credit exists. Credit is communicated as an absolute delivery-limit (`delivery-count + link-credit`), not an increment, which makes `flow` idempotent [3 §2.6.7]. `drain` forces the sender to consume all outstanding credit and report, turning an indefinite wait into a definite answer; `echo` requests the partner's state so a receiver can tell when a stopped link has quiesced [3 §2.6.7, §2.6.10, §2.7.4]. Defaults in the field: RabbitMQ 170 link credits with a low-water mark of 85, session window 400, internal queue-credit batches of 256 [16]; Artemis 1000/300 [41; 54]; Classic 1000 [56]; Service Bus one credit per receive, or `PrefetchCount` credits [57].

**P13 — Large messages and streaming bodies.** Maximum: `attach.max-message-size`, unset or zero meaning unlimited, violation giving `amqp:link:message-size-exceeded` [3 §2.7.3, §2.8.18]; independently `open.max-frame-size` bounds a frame, default `4294967295`, floor 512 [3 §2.7.1]. A message exceeding the frame size is split with `more=true` on all but the last transfer; deliveries on one link MUST NOT interleave but deliveries on different links may; `aborted=true` on the last transfer tells the receiver to discard everything so far and implicitly settles the delivery [3 §2.6.14, §2.7.5]. **Yes, a body can be delivered before it is complete**: the transport hands payload up as it arrives, the `received(section-number, section-offset)` state exists precisely to describe a partially transferred body, and a receiver may report non-terminal states mid-delivery for exactly this reason [3 §2.6.12; 4 §3.4.1]. Proton exposes it as `Delivery.partial`, true when not all delivery data is available [30]. Broker practice varies: Artemis selects an AMQP large-message reader only once enough bytes identify the message as large, writes bytes incrementally, and calls `onMessageComplete` only after a non-partial transfer, so it does not route a body before receipt completes; `amqpMinLargeMessageSize` = 102400, `-1` disables [45; 54]. Service Bus caps at 256 KB on Standard and up to 100 MB on Premium, with frame sizes of 262144 and 1048576 bytes respectively [57; 60].

**P14 — Identity.** Peers authenticate through SASL (RFC 4422) in a dedicated protocol layer, the server advertising mechanisms in preference order and the client required to use the highest-level profile it can handle; TLS client certificates authenticate at the TLS layer, and SNI can select both the back end and the credential-validation domain [6 §5.2-5.3]. Per-message identity: exactly one field, `properties.user-id`, client-set, possibly authenticated by intermediaries, immutable because it is in the bare message [4 §3.2.4]. Authorization granularity: none in the core standard beyond `amqp:unauthorized-access`, `amqp:not-allowed`, `amqp:resource-locked` and the ability to refuse an `attach` with a null terminus [3 §2.6.3, §2.8.15]. Brokers supply it: Artemis per address, wildcard or exact, with `send`/`consume`/`browse`/`manage`/`createAddress` and queue-level restriction through FQQN, though a send cannot be constrained below the address [46]; RabbitMQ per virtual host selected via `open.hostname` [14]; Service Bus `Send`/`Listen`/`Manage` per entity, enforced through `$cbs` `put-token` with an audience [57].

**P15 — What a hostile or buggy peer can make you allocate.** Accepting the defaults means agreeing to a single frame of up to 4 GiB (`max-frame-size` `4294967295`), 65536 sessions (`channel-max` 65535), 2^32 links per session (`handle-max` `4294967295`), messages of unbounded size (`max-message-size` unset), and a connection that never idles out (`idle-time-out` unset) [3 §2.4.5, §2.7.1-2.7.3]. Attack surfaces the spec itself names: an unsettled map too large to encode in a frame, whose only defence is `incomplete-unsettled` plus the mandatory detach/reattach cycle, which bounds the frame and not the map [3 §2.6.3, §2.7.3]; link names "arbitrarily long without a significant penalty" [3 §2.6.1]; and 32-octet delivery tags times an unbounded number of unsettled deliveries. Defences: set every limit explicitly and lean on the two credit schemes, the only bounds that start closed [3 §2.6.7, §2.7.2]. `application-properties` bounds nesting by excluding maps, lists and arrays [4 §3.2.5]; annotations and the body have no such restriction. Filter Expressions adds compute exhaustion via complex expressions [9 §7.1]. Brokers cap far harder than the spec's defaults: Dispatch `maxFrameSize` 16384 and `maxSessions` 32768 [27]; Artemis `maxFrameSize` 131072 [54]; Service Bus one session per connection, 5000 AMQP connections per namespace, 5000 concurrent receive requests per entity [57; 60].

**P16 — Observability.** `disposition` is the receipt: it certifies the delivery's state at the issuing endpoint and, with `settled=true`, that the endpoint has forgotten it [3 §2.6.12, §2.7.6]. Counters visible on the wire: `flow.available` (the sender's backlog), `flow.delivery-count` and `flow.link-credit` (both ends' positions), `header.delivery-count` (prior failed attempts on this message) [3 §2.6.7; 4 §3.2.1]. `flow.echo` lets a peer demand the partner's current state on request [3 §2.7.4]. `error.description` carries loggable text and `error.info` a structured map [3 §2.8.14]. Extension points for tracing: `message-annotations` with `x-opt-` keys, which MUST be ignored if not understood and which intermediaries MUST propagate — the natural place for trace context [4 §3.2.3, §3.2.10] — plus `open.properties`, `begin.properties`, `attach.properties` and `flow.properties`, each with a registry [3 §2.7.1-2.7.4]. `footer` carries values computable only once the whole message is seen [4 §3.2.9]. There is no metrics or statistics protocol; management is an extension [12; 57; 58]. Broker-specific signals: RabbitMQ reports `rabbitmq:active` in `flow.properties` for quorum-queue single-active-consumer state, and puts `queue` and `reason` in a rejection's error info map [14].

**P17 — Shutdown, in-flight and queued messages.** Teardown is link, then session, then connection, each explicit. Link: `detach(closed=true)` destroys the endpoint at both ends [3 §2.6.6]; `detach` without `closed` unmaps the handle but leaves the endpoints able to communicate indirectly through the session, because deliveries referenced by delivery-id are still live [3 §2.6.4]. This is deliberate: "The disposition performative MAY refer to deliveries on links that are no longer attached. As long as the links have not been closed or detached with an error then the deliveries are still 'live' and the updated state MUST be applied" [3 §2.7.6]. Session `end` and connection `close` each keep reading until the partner answers, and `close` MUST be the last thing written [3 §2.4.3, §2.5.2]. The drain primitive is `flow(drain=true)`, which makes the sender consume all outstanding credit and report so a consumer can shut down knowing nothing more is coming; `flow(link-credit=0, echo=true)` reaches quiescence without consuming credit [3 §2.6.7, §2.6.10]. There is no linger timer: an unsettled delivery at shutdown is not lost but *in doubt*, and its fate is decided by resumption or by `source.default-outcome` when the receiver's state can no longer be learned [3 §2.6.13; 4 §3.3, §3.5.3]. Queued messages at the node are unaffected by client shutdown; the terminus survives per `expiry-policy` and `timeout`, with `session-end` and `connection-close` the policies that start counting down at these events [4 §3.5.6]. RabbitMQ notes that detaching directly requeues unacknowledged transfers, whereas stopping the link and acknowledging first hands over cleanly [16].

**P18 — Transports.** The core standard defines TCP on port 5672 plus TLS-over-TCP on 5671, and explicitly reserves but does not define UDP and SCTP [3 §2.8.19]. TLS is a layer selected by protocol-id `%d2` with in-band upgrade, or an out-of-band pure TLS listener on 5671; SASL is `%d3`; bare AMQP is `%d0`; layers nest [6 §5.1-5.3]. WebSocket is a separate Committee Specification 01 (16 August 2016): open a WebSocket with `Sec-WebSocket-Protocol: amqp`, expect HTTP 101 echoing the subprotocol, then send each protocol header as the contents of a single WebSocket message; thereafter AMQP frames travel as binary WebSocket message payloads with *no* mapping between AMQP frames and WebSocket messages or frames in either direction — one AMQP frame may span several, and one may contain several. One WebSocket connection is one AMQP connection, the Request-URI has no defined meaning, and the `Host` header identifies the container. SASL is allowed, but SASL mechanisms providing encryption are not supported by the binding. `open.properties` gains `redirect-schemes` and redirect info maps gain `scheme` and `path` [8 §§2-3]. Default ports for the URI schemes: `amqp` 5672, `amqps` 5671, `ws` 80, `wss` 443 [10 §3.1]. No IPC, in-process or QUIC transport is defined in the core standard or the reviewed extensions. What changes between transports: the header exchange (protocol-id, and over WebSocket the one-header-per-message rule), framing (raw byte stream versus WebSocket binary messages), the redirect vocabulary, and — for alternative TLS establishment — whether a header precedes TLS at all [6 §5.2.1; 8 §2].

The API warns that calling send with zero credit buffers locally and makes reported credit go negative — a library convenience, not wire permission [30].

**Notable deployments.** Azure Service Bus and Azure Event Hubs [57; 59]. The standard's editors came from JPMorgan Chase, Microsoft and Red Hat, and the TC chairs from Microsoft and INETCO [1].

**Known incompatibilities.** No vendor publishes an interoperability matrix. What the sources document, and — marked as such — what one client's runs against a foreign implementation measured [67]:
- *Settlement.* `rcv-settle-mode=second` is refused by Artemis, whose test comments "The Broker does not currently support ReceiverSettleMode of SECOND" [54]; RabbitMQ lists exactly-once as unsupported [14]; Service Bus has no link recovery, so `second` cannot deliver its guarantee there either [57]. A client written against the spec's exactly-once dance will not get it from any of the three. **Measured:** an acceptor supporting both receiver settle modes honoured `second` in its answering `attach`, and the same acceptor restricted to `first` did not claim otherwise [67] — so this is a broker-by-broker fact and not a statement about implementations, and the answer is in the `attach` either way (§6.2).
- *Transactions.* RabbitMQ implements none [14]; Artemis allows one transaction per session despite `amqp:multi-txns-per-ssn` [41]; Dispatch supports local transactions only, to a single broker, and no XA [26 §§1.2, 11.2.2]; Part 6 Distributed Transactions was never published [5 §4.5.3].
- *Filters.* Three generations coexist. Apache's `apache.org:selector-filter:string` (`0x0000468C:0x00000004`) and `apache.org:no-local-filter:list` (`0x0000468C:0x00000003`), with capabilities `APACHE.ORG:SELECTOR` and `APACHE.ORG:NO_LOCAL`, are described as *proposed* AMQP 1.0 filters, not a standard registry [33]. OASIS Filter Expressions CSD 01 defines an entirely different `amqp:*-filter` family with codes in the `0x100`-`0x178` range and its own capability names [9]. Brokers add vendor filters: `rabbitmq:stream-filter`, `rabbitmq:stream-match-unfiltered` [19] and `com.microsoft:session-filter` [37]. A client must negotiate rather than assume.
- *Service Bus filter-set encoding.* Proton's own Service Bus example notes that a bare AMQP string is technically not a valid filter-set value unless described, and that Service Bus's behaviour may change [37].
- *CBS.* Service Bus's `put-token` envelope (`application-properties` `operation`, `type`, `name`, `expiration`) and OASIS CBS CSD 01's `set-token` message (`subject`=`set-token`, optional `token-type`, disposition-signalled result) are different wire contracts, and the token type naming differs (`jwt` versus `amqp:jwt`) [57; 11].
- *WebSocket subprotocol.* OASIS WSB CS 01 normatively requires `Sec-WebSocket-Protocol: amqp` [8 §2.1]. The commonly cited `amqpwsb10` appears in no official source reviewed here.
- *Management.* Service Bus states outright that it "does not currently implement any core feature of the AMQP Management specification", implementing the draft's request/response pattern with `com.microsoft:`-prefixed operation names instead: `renew-lock`, `peek-message`, `schedule-message`, `cancel-scheduled-message`, `renew-session-lock`, `set-session-state`, `get-session-state`, `get-message-sessions`, `add-rule`, `remove-rule`, `enumerate-rules`, `receive-by-sequence-number`, `update-disposition` (with `disposition-status` values `completed`, `abandoned`, `suspended`), each admitting an optional `com.microsoft:server-timeout` in milliseconds, with replies carrying `correlation-id` plus `statusCode` and optional `statusDescription` using HTTP status conventions [57; 58]. RabbitMQ's Java and .NET AMQP client wrappers manage topology through the HTTP-over-AMQP extension [15]. There is no interoperable management surface.
- *Address syntax.* Every broker invented its own: RabbitMQ v2 `/queues/:q` and `/exchanges/:x/:rk` [14], Artemis plain names plus `address::queue` [43], Service Bus entity paths [57], Classic `queue://`/`topic://` [56], Broker-J exchange-or-queue [35]. The core standard leaves `address` undefined [4 §3.2.15] and the Addressing draft that would fix it is a 2021 CSD 01 [10].
- *A duplicate link name: steal or refuse.* Part 2 §2.6.1 makes the link name plus direction unique between two containers and gives the remedy for a second `attach` of a name already in use — the existing link is stolen, the loser detached with `amqp:link:stolen` [3 §2.8.18]. **Measured:** a foreign implementation refused the second `attach` of a name it still held, with a reason naming the duplication, rather than implementing the steal [67]. Both behaviours are visible to the same client code only if it treats an attach as something that can fail; one that assumes the steal will hold a handle the peer has no link for. **The same implementation's next minor version behaves otherwise** (`fe2o3-amqp` 0.18.4, 2026-10-23, the client of [67] against it over loopback): when the stealing client sends `detach(error=amqp:link:stolen)` before its second `attach`, the peer answers the `detach`, accepts the new `attach` and reuses the freed handle — and its `flow` for the old link crossed the `detach` on the wire. A client that reads §2.6.5's errant-link rule as covering frames the peer sent before it saw the `detach` ends the session over that crossing; the client now treats input on such a handle as errant only after the peer's answering `detach`.
- *Terminus properties in the answer.* Terminus attributes are requested by the attaching peer and reported as actually created by the other [3 §2.6.3]. **Measured:** a foreign implementation echoed `expiry-policy=never` and `timeout=600` back unchanged [67], while RabbitMQ documents terminus expiry policy as not supported at all [14]. The same `attach` therefore gets an honoured request from one peer and a substituted or absent terminus from another, and only the answering `attach` says which.
- *Transactional capability is discoverable.* **Measured:** an implementation built without its transaction feature offered **none** of Part 4's five coordinator capabilities in the answering `attach`'s `offered-capabilities` [67]. That is the cheap pre-check: a client can read the absence at attach time instead of discovering it when `declare` is refused or ignored. The names to look for are the five of §6.6 — `amqp:local-transactions` and its relatives — and *not* an `amqp:txn:` prefix, which belongs to the transactional state and the transaction error conditions [5 §4.5.1, §4.5.5].
- *Not measured, and still only documentation.* RabbitMQ 4.x's four published non-supports — link suspend/resume, resumed deliveries, exactly-once, terminus expiry policy [14] — were **not** exercised: no RabbitMQ 4.x was reachable on the machine that produced [67]. They remain what the vendor says rather than what a wire run observed, and the open question is whether each is a refusal a client can read (an answering `attach` reporting something else, a `detach` with a condition) or a silent substitution. The distinction decides whether a portable client can negotiate or must be configured per broker.

67. Measurement record, *AMQP 1.0 client against `fe2o3-amqp` 0.17.0 in both roles*, 2026-09-12, Linux x86-64, rustc 1.98, loopback TCP, no broker present. The peer is minghuaw's `fe2o3-amqp` [62], installed from crates.io with its `acceptor` feature and **without** its `transaction` feature, driven through `fe2o3_amqp::acceptor::{ConnectionAcceptor, SessionAcceptor, LinkAcceptor}`; the client is an independent AMQP 1.0 implementation written against [2], [3], [4] and [5], taking the sender and the receiver role in turn across eight scenarios. Used for: what that acceptor declares in `open` (`max-frame-size=262144`, `channel-max=255`, **no `idle-time-out`**); a `flow` arriving for a link handle immediately after that link was cleanly detached; an 8192-octet message crossing as several `more=true` `transfer` frames against an acceptor built with **`max_frame_size(1024)`** and arriving whole; a body carried as `data` sections refused with a descriptor mismatch by a deserialiser asked for an `amqp-value` binary; `rcv-settle-mode=second` honoured in the answering `attach` under `SupportedReceiverSettleModes::Both` and not claimed under `First`; `expiry-policy=never` with `timeout=600` echoed back unchanged; a second `attach` of a link name the peer still held refused with a reason naming the duplication rather than stealing the link; a re-attach of a released name carrying no `unsettled` map answered as a new link with nothing recovered; and none of Part 4's five coordinator capabilities among the peer's `offered-capabilities`. **RabbitMQ 4.x was not reachable on this machine**: `rabbitmq-server`, `docker` and `podman` were all absent, so none of the four non-supports it publishes [14] was exercised and none of them is recorded here as measured.
